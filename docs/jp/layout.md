# キャンバスレイアウト

Node-RED のノード配列のための、単体で動くレイアウトエンジン。UMD モジュールで、
`window.LLMPlugin.CanvasLayout` または `require('./src/core/canvas_layout.js')` として使う。
ノードの幅を考慮し、鎖(つながったノード)は `(widthA + widthB)/2 + edgeGap` の間隔で詰めて並べる。
幅の広いラベルを持つノードは、隣のノードを自動的に押し出す。

## 例

### 1. 全体再レイアウト(full reflow)

```js
const Layout = require('./src/core/canvas_layout.js');
const flow = [
    { id: 'a', type: 'inject',   wires: [['b']] },
    { id: 'b', type: 'function', wires: [['c']] },
    { id: 'c', type: 'debug',    wires: [] }
];
Layout.reflowCanvasNodes(flow, { startX: 100, startY: 100 });
// inject=120, function=140, debug=120 (grid-snapped from estimate)
// leftEdges:    a=100,         b=260 (=100+120+40),  c=440 (=260+140+40)
// x (centres):  a=160,         b=330,                c=500
// y all 100 (single row, single component)
```

### 2. 既存の2ノードの間にノードを挿入

```js
const merged = [
    { id: 'a', type: 'inject',   x: 100, y: 100, wires: [['n']] },
    { id: 'n', type: 'function', wires: [['b']] },                  // new (140-px wide)
    { id: 'b', type: 'debug',    x: 280, y: 100, wires: [] }
];
Layout.placeAddedNodesNearNeighbors(
    merged,
    { a: true, b: true },
    { a: { x: 100, y: 100 }, b: { x: 280, y: 100 } }
);
// a stays at 100, n placed centre 270 (left edge 200 = 100+60+40), then
// Step 3.4 shifts b right so its left edge sits at n.right+40=380 (b.x=440).
```

### 3. 純粋なトポロジカル位置(ピクセルなし)

```js
const positions = Layout.layoutNodes(
    ['a', 'b', 'c'],
    { a: ['b'], b: ['c'], c: [] },
    { a: [], b: ['a'], c: ['b'] }
);
// { a:{col:0,row:0,comp:0}, b:{col:1,row:0,comp:0}, c:{col:2,row:0,comp:0} }
```

### パスの順序と、その順序である理由

インポータは内側から外側へ順にパスを走らせる。**箱の中身を置く → 箱を中身に合わせる →
箱同士を並べる**、という順である。各パスは前のパスが終わっていることを前提にしているので、
順序を入れ替えるとどこかで辻褄が合わなくなる。

| # | パス | 前提 |
|---|------|------|
| 1 | `keepLeftEdges` | なし。**入力**の座標を先に直すパスで、これ以降のすべてが「正しい左端」を前提に判断できるようになる。動かした ID は 2 の `reflowIds` にも渡される。 |
| 2 | `reflowCanvasNodes` / `placeAddedNodesNearNeighbors` | (1)。メンバーを配置する。列・行・キャプションまで決める。 |
| 3 | `repositionSubsetByAliases` | (2)。指定された一部だけをその場で組み直すので、全体の配置より後に走らせないと結果が打ち消されてしまう。そのあと、もとからある junction ノードを置き直す。鎖は junction ノードを通して並べるが、レイアウトが junction ノードの位置を自分で決めることはない。junction ノードと、枠の外にある link ノードは元の位置に戻し、つなぐ先が動いた分だけずらす([junction ノードはつなぐ先に付いていく](#junction-ノードはつなぐ先に付いていく)を参照)。 |
| 4 | `fitGroups` | (2)(3)。枠はメンバーが落ち着いた位置に合わせるものなので、配置より前には走れない。すべての枠をメンバーにぴったり合わせる。 |
| 5 | `separateGroups` | (4)。枠に入った各シーケンスをメンバーの左端で揃え、そのあと枠同士の衝突を解消する(下記)。枠同士を `groupGap` だけ離すのはこのパスである。どちらも枠の範囲を読むので、枠が確定していなければ成り立たない。 |
| 6 | `applyCommentAnchors` | (5)。上のパスが残した位置から読み直し、各キャプションを見出すノードの上へ戻す。ノードに乗ってしまう位置は 1 行上へ引き上げる。 |
| 6½ | `snapToGrid` | (6)。今回の編集で置いたもの・動いたものをすべてマス目に乗せる([すべてマス目の上に](#すべてマス目の上に)を参照)。吸着で動いたノードも 7 で離せるように、7 より前に走る。7 はマス単位で押すので、押されて元の位置から動いたものも続けて吸着させ、何も動かなくなるまでこの 2 つを繰り返す。 |
| 7 | `settleCollisions` | (6)。上のパスを信用せず、結果そのものを確かめる不変条件のパス。次の 3 つを満たすようにする。ノード同士が重ならない。枠同士が重ならない(`groupGap` より近づかない)。メンバーでない枠の中にノードが入らない。コメントも対象にする。同じ階層の兄弟どうしで比べ、誰が置いたかに関係なくすべての衝突を解消する。重なったときは、下側を丸ごと(枠なら中身ごと、つながった鎖ならキャプションごと)上側の下へ移す。ただし同じ鎖の中では、下側のノードだけをキャプションごとずらす。どこにも紐づかないコメントは、そのコメントのほうを動かす。枠の外の junction ノードは、つなぐ先と一緒に動く。junction ノード(実寸の 10×10 で測る)をそれ自体の都合で動かすことはない。junction ノードに載ったものを下へどけ、枠の縁にある junction ノードは普通の配線経路なのでそのままにする。つなぐ先に載った link ノードは、それだけをどける。枠の外からメンバーを見出していて枠線に乗っているキャプションは、その枠に入れる。移すたびに枠を合わせ直し、移した先でまた当たれば、それも順に解消する。物を引き離す最後のパスなので、キャプションの配置はその前に済ませる。 |
| 8 | `ensureCanvasMargins` | (7)。各軸につき、全体を同じ量(マス単位)だけずらすだけなので、上のどの間隔も崩さない。何かをずらしたときは 6½ と 7 をもう一度走らせる。マス目から外れていたノードも、これで「動いた」ことになるからである。 |

この順序が避けているのは「古い大きさのまま残った枠」である。それを許すと 5 が、中身の
シーケンスではなく取り残された矩形のほうを揃えてしまう。

## 公開 API

| 関数 | 用途 |
|----------|---------|
| `layoutNodes(aliases, outgoing, incoming)` | 純粋なトポロジカルレイアウト。`{ alias: { col, row, comp } }` を返す。 |
| `reflowCanvasNodes(nodes, options?)` | キャンバス全体の再レイアウト(全位置を再計算)。 |
| `placeAddedNodesNearNeighbors(nodes, existingIdMap, basePositions, options?)` | 増分レイアウト(既存ノードは固定し、新規のみ配置)。 |
| `estimateNodeWidth(node, options?)` | ラベルに基づく幅の推定。`gridSize` にスナップする。 |
| `getNodeWidth(node, options?)` | `options.getNodeWidth(node)` があればそれを、なければ `estimateNodeWidth` を使う。 |
| `computeComponentYOffsets(ids, positions, startY, spacingY, gap, nodeHeight?, gridSize?)` | 縦に積むための、コンポーネントごとの Y オフセット。`spacingY` と `gap` はエッジ間の値。行ピッチは `nodeHeight + spacingY`、コンポーネントのステップは `nodeHeight + gap` で、どちらも `gridSize` の倍数に切り上げる。`nodeHeight` と `gridSize` のデフォルトは `LAYOUT_DEFAULTS`。 |
| `snapToGrid(nodes, options?)` | 各ノードの左端と中心 y をマス目に乗せる。キャプションは見出すノードの左端に揃える。`options.keep` に挙げた id は動かさない。枠は合わせ直す。[すべてマス目の上に](#すべてマス目の上に)を参照。 |
| `fitGroups(nodes, options?)` | すべてのグループの枠をメンバーに合わせる。[グループの枠](#グループの枠)を参照。 |
| `separateGroups(nodes, options?)` | グループの枠の左端を揃え、外側のものから離れるまでブロックを押し下げる。離す量は、枠なら `groupGap`、素のノードならパディング 1 つ分多い値。`fitGroups` のあとに走る。 |
| `keepLeftEdges(nodes, widthsBefore, options?)` | 幅が変わったノードの中心を計算し直し、**左端**を元の位置に保つ。動かした ID を返す。 |
| `ensureCanvasMargins(nodes, options?)` | いちばん上/左の端(枠を含む)がキャンバスの端から `topMargin` / `leftMargin` より近いとき、軸ごとに全体を同じ量だけずらす。 |
| `settleCollisions(nodes, options?)` | キャンバス上のすべての衝突を解消する。対象は、ノードやキャプション同士、枠同士、メンバーでない枠の中のノード。動かした ID を返す。 |
| `routingAnchors(nodes)` | 枠の外にある junction ノード・`link in`・`link out` ごとに、それがつなぐ先のノードを返す。[junction ノードはつなぐ先に付いていく](#junction-ノードはつなぐ先に付いていく)を参照。 |
| `LAYOUT_DEFAULTS` | デフォルト定数。 |

## デフォルト

```js
LAYOUT_DEFAULTS = {
    startX:         60,    // 最初の列の左端
    startY:         60,    // 最初の行の「上端」。startX と同じく端の座標
    spacingY:       40,    // 縦に積んだ行どうしの、エッジ間の余白
    componentGap:   60,    // つながっていないコンポーネントどうしの、エッジ間の余白
    edgeGap:        40,    // 隣り合うノードの、エッジ間の余白(横方向)
    minNodeWidth:  100,    // Node-RED の MIN_NODE_WIDTH
    nodeHeight:     30,    // Node-RED が描画する標準のノードの高さ
    gridSize:       20,    // Node-RED のキャンバスのマス目。幅、縦のピッチ、すべての位置が従う
    topMargin:      20,    // キャンバス上端(y=0)と最上端の実体との最小の間隔
    leftMargin:     20,    // 左端(x=0)側も同じ。グループの枠も対象
    groupPadding:   25,    // エディタ自身が取る、グループの枠とメンバーとの余白
    groupGap:       10     // 枠と枠の間隔。メンバー間の componentGap から両側のパディングを引いた値
};
```

`spacingY`, `componentGap`, `edgeGap` はすべて**エッジ間**のクリアランス(見える余白)を
表し、中心間距離ではない。レイアウトエンジンは中心座標が必要になるたびに内部で
`nodeHeight` を加え、縦のピッチはマス目の倍数に切り上げる(下記)。

### すべてマス目の上に

エディタはドラッグされたノードを、**左端**(または右端)と**中心の y**でマス目に吸着させる
(`RED.view.tools.calculateGridSnapOffsets`)。レイアウトがそれ以外の位置に置いたノードは、
ドラッグした瞬間に跳ねてしまい、隣のノードと手で揃えられない。そこで、次のようにしている。

- **横方向**は、左端が構成上つねにマス目の倍数になる。`startX`、`edgeGap`、すべての幅
  (`estimateNodeWidth` もエディタ自身の `w` も)がマス目の倍数だからである。中心は
  `leftEdge + width / 2` で求める。中心のほうを吸着させると、同じ列にある 100px のノードと
  120px のノードが半マスずれてしまう。
- **縦方向**は、ノードの高さが 30px なので、ノード間をマスちょうどの隙間にすると両方の中心を
  マス目に乗せられない。そこでピッチを切り上げる。`rowPitch = ceil((nodeHeight + spacingY) / grid) * grid`
  = 80、かたまりのステップ `ceil((nodeHeight + componentGap) / grid) * grid` = 100 である。
  シーケンス同士の間は 70px、つまり空きマス 3 つと、各ノードの中心線が切り取る半マスになる。
  最初の行の中心も、`startY + nodeHeight / 2` を同じように切り上げて決める。
- 縦に動かすパスは、すべて**マス単位**で動かす。`settleCollisions` は押す量を、
  `ensureCanvasMargins` はずらす量を、`placeAddedNodesNearNeighbors` の帯の押し下げは `dy` を、
  それぞれ切り上げる。前後のノードの間に置くノードは、その平均に最も近いマス目の線に置く。
- それでもマス目から外れて来たもの(古いレイアウトや手で置いたフロー)は `snapToGrid` が拾う。
  吸着させるのは、今回の編集で**置いたもの・動いたもの**のすべてである。編集前とまったく同じ位置に
  残ったものは、マス目から外れていてもそのままにする。プロパティを変えるだけの編集では、
  何も動かないようにするためである。
    - 見出すノードの列にすでに揃っているキャプションは、その列を保つ(マス目から外れるのは、
      そのノードが元の位置に残された場合だけ)。それ以外のキャプションは、自分自身をマス目に乗せる。
    - ノードに接しているキャプション(ノードの高さの整数倍だけ上にあるもの)は、接したままでいる
      よう、ノードと一緒に上下に動く。それより離れたものは、y を**上へ**切り捨ててマス目に乗せる。
    - junction ノードは吸着させない。junction ノードはワイヤが置いた場所に留まる。
- 整列(`reposition`)では、組み直した部分を元の左上へ戻すとき、ちょうどの位置ではなく
  最も近いマスに戻す。組み直しでマス目に乗った部分を、マス目から外れた元の角へぴったり戻すと、
  その角にあったノードだけがマス目から外れて残る。「揃えて」と頼んだのに、手で揃え直すものが
  残ってしまっていた。
- `settleCollisions` は、ほかと同じくグループへの所属を**どちら側からでも**読む(メンバーの `g`、
  またはグループの `nodes` 一覧)。`g` だけで読むと、一覧にだけ載ったメンバーが自分の枠の外に
  いることになり、押すたびに両方が動いて、フローが数万 px 下まで飛んでいた。押しても離せない
  組み合わせ(どちらも押される側と一緒に動くもの)は、そのままにする。

キャプションは見出す対象に**接して**置く。ノードの `nodeHeight`(30px)上に置き、キャプションを
積むときも同じ間隔で上げるので、どこにも隙間はできない。30 はマス目の倍数ではないので、
キャプションの y はマス目から半マスずれる。キャプションはノードと一緒に動く見出しであり、
それだけで揃えるものではないからである。

そのノードのキャプションと認識できる近さのスタックは、古いレイアウトが残した 40px も含めて、
常にノードに接するよう詰め直す。「認識できる近さ」とは、各間隔が `touchingTol`
(= マス目に切り上げた 1 段 + 1 マス)以内であることをいう。それより離して置いたものは、
その位置のままにする。

コメントは、その**左端**がアンカー対象の左端に一致するよう配置される
(`commentX = target.leftEdge + commentWidth / 2`)。追加のスナップは行わない。そのため、
幅の広いキャプションも軸から外れず、見出すノードと同じ列に揃って見える。

すべてのレイアウト関数は、これらの既定値を上書きするオプションを受け取る。増分レイアウトは
さらに、どこにも繋がらない新規ノードをまとめて置く帯の間隔として `bandGap`(既定は
`componentGap` と同じ)を受け取る。またどちらの関数も、何をキャンバス上の実体とみなすかの
判定を差し替えられる(既定はタブ定義とサブフロー定義以外をすべて対象とする)。

どちらの入口も、最後に**上端のはみ出し防止**を通る。コメントのスタックは対象ノードから上へ
伸びるので、キャンバス上端に近いノードにキャプションを足すと、画面の外へ出てしまうことがある。
いずれかのノードの上端が既定の余白(20px)より上に来た場合は、全ノードを同じ量だけ下へ
平行移動する。相対的な位置関係は保たれ、フロー全体が下へスライドするだけである。位置を
固定したまま 1 つのコンポーネントだけを組み直す処理は、この防止をスキップする。呼び出し元が
最後にキャンバス全体をまとめて見るためである。

### `ensureCanvasMargins` — 上と左に同じだけ空ける

唯一の余白ガード。上端と左端を同時に見て、ノードだけでなく**グループの枠も**数える。枠は
メンバーより `groupPadding` だけ外側に描かれるので、ノードだけで測ると枠が端に寄る(あるいは
キャンバスの外へ出る)。上端近くのノードの上に積まれたキャプションもここで拾う。全体を軸ごとに
同じ量だけずらすので、相対的な位置関係は変わらない。

**原点はどちらも「端」である。** `startX` は最初の列の左端、`startY` は最初の行の上端で、
行の中心はそこから半ノード分下を、マス目に切り上げた位置になる。以前は `startY` だけが中心を
指していたため、フローは左端より 15px だけ上に寄り、それを囲む枠はさらに上に寄っていた。
原点の意味を揃えたことで、素のフローでも枠つきのフローでも、上と左の余白は、マス目への丸めが
残す 5px の差を除いて等しくなる。

## 幅が変わっても左端は動かさない

ノードの `x` は**中心**なので、名前を変えると左右両方の端が動く。一方、このエンジンが揃えて
いるのは左端である。そのため、リネームしたノードは自分の列からずれ、上のキャプションだけが
取り残されていた。名前が十分に長いと、左端(とそれを囲む枠)がマイナス方向へはみ出すこと
もあった。

`keepLeftEdges(nodes, widthsBefore, options)` が、配置パスの前にこれを直す。幅が変わったノード
について、元の左端から `x` を求め直す。戻り値は動かした ID の一覧で、インポータはそれを
`placeAddedNodesNearNeighbors` の `options.reflowIds` として渡す。幅が増えたノードは以前より
右まで届くので、挿入があったときとまったく同じ扱いでそのコンポーネントを組み直す。その結果、
後続のノードは重ねられるのではなく右へずれる。

キャプション側も同じ規則に揃えた。`applyCommentAnchors` は、記録時の中心のずれを再生するの
ではなく、対象ノードの**左端**をキャプションに与える。中心のずれの再生は、双方の幅が変わらない
間しか整列を保てなかった。

## 幅を考慮した間隔

```text
distance(a, b) = (width(a) + width(b)) / 2 + edgeGap
```

この式を実際の座標に落とす処理(`computeLeftEdges`)は、変換器と再配置で共有している。変換器は
エイリアスをキーにして呼び(この時点ではまだノードの id がない)、再配置は id をキーにして呼ぶ。
両者は同じ数値に着地しなければならない。スキーマを変換してから再配置しても何も動かない、
というのが条件である。以前は同じ処理が 2 か所に書かれており、片方に「もう一方と揃えること」
という注記が付いていた。

幅は、まず呼び出し元が渡した取得関数を試し、なければラベルからの推定に切り替える。取得関数を
渡せるので、呼び出し元はエディタが実測した幅を使える。正確な幅が分かれば、隣り合うノードの
あいだには、ラベルの長さによらず指定した余白(既定ではグリッド 2 マス分)がちょうど空く。
推定に切り替えた場合の式は、エディタ自身の描画コードの式を写したものである(Node-RED 4.1.7 で確認)。

```text
w = max(node_width, 20 * ceil((labelTextWidth + 50 + (inputs>0 ? 7 : 0)) / 20))
```

`labelTextWidth` は文字ごとに推定する(ラテン文字は約 7.5px、CJK / 全角は約 14px)。
chrome(ラベル以外の部分の幅)はノードの種類によって異なる。

- **通常ノード**(inject, function, debug など): chrome = 57px(エディタの 50px の chrome に、
  入力ポートのスタブ 7px を加えたもの)。入力のない型では差が 7px 以下になり、グリッドスナップに
  吸収される。
- **コメントノード**: chrome = 24px。実際に描画されたコメントに経験的に合わせた値である
  (アイコンが小さく、ポートの出っ張りもない)。ここを大きくすると、幅の広いキャプションが
  対象ノードの左端より右へ押し出されてしまう。

インポート時の既定である `edgeGap = 40` では、既定名のままの約 120px のノード 2 つは、中心間が
約 160px になり、あいだにグリッド 2 マス分の余白が残る。ユーザーが Node-RED でノードを 1 つずつ
ドラッグして置いたときにできる間隔とほぼ同じである。

## グループの枠

グループの枠は**グループ自身に保存される**(`x` / `y` / `w` / `h`)。Node-RED がこれを
再計算するのは、ユーザーがメンバーを枠へ、あるいは枠の中でドラッグしたときだけである。
つまり、メンバーを動かした側が枠の責任を持つ。`0 × 0` の枠でインポートしたグループは、
ユーザーにも `0 × 0` に見えるし、レイアウトで下へ押し出されたメンバーは枠を置いていく。
`fitGroups` はレイアウトの各パスのあとに走り、これを解決する。

- 枠はメンバーの外接矩形を、四方に `groupPadding`(25)だけ広げたものである。
  `RED.group.addToGroup` が付けるクリアランスと同じなので、プラグインが合わせた枠と
  エディタが合わせた枠は同じ見た目になる。
- ノードの端は、中心と `getNodeWidth` / `nodeHeight` から求める。**入れ子**のグループは
  `x` / `y` がすでに左上隅なので、内側の枠を先に(深い順に)合わせ、そのあと外側がそれを包む。
- ユーザーが大きくした枠も含め、**すべての**枠を中身にぴったり合わせる。中身より大きい枠は、
  中身を基準に揃えたり離したりできないからである。
- グループはノードとしてはレイアウトしない(`isLayoutNode` が除外する)ので、何かを
  押しのけることはない。裏を返すと、枠同士を離しておくものも何もない。ノードのレイアウトが
  空けるのは**メンバー**の間隔であり、`componentGap` からパディング 2 つ分を引くと、枠と枠の
  間は 20px になる。しかもグループに入ったコメントが枠を 40px 上へ伸ばすので、枠は重なって
  しまう。そこで `separateGroups` を `fitGroups` のあとに走らせ、枠が外側のものと離れている
  ことを保証する。

### `separateGroups` — 枠を揃え、離す

- 縦に並んだシーケンスは 1 つの列として読まれるので、**左端を揃える**。揃えるのは枠の線では
  なく**シーケンス自身**(メンバーの左端)である。整列はブロック単位ではなく
  **枠単位**で行う。互いにワイヤでつながった 2 つのシーケンスは 1 つのブロックになるが、
  再配置(`reposition`)が生むのはまさにその「段違い」だからである。
- 枠は中身ごと動く。メンバー、そのまたメンバー、そしてメンバーを見出すキャプションを
  連れていく。ただし、同じブロックに**どの枠にも属さないノード**がある場合は動かさない。
  チェーンの途中を囲んだ枠の上流側や、枠の末尾からぶら下がったノードがそれにあたる。枠だけが
  動き、その間のワイヤがねじれてしまうからである。その枠だけにつながる junction ノードは
  これにあたらず、枠と一緒に動く。枠同士が互いを妨げることはない。
- 整列するのは**縦に積まれた**シーケンスだけである。行(縦方向)が重なっている枠同士は、
  横に並んでいるか、一方のノードがもう一方のノードとワイヤでつながって噛み合っている。
  それらを同じ列へ引き寄せると、シーケンスが別のシーケンスの上に落ちてしまう。
- 誰が描いたかに関係なく、縦に積まれた枠はすべて**いちばん左**のシーケンスに揃える。
  キャンバスの余白は、そのあと `ensureCanvasMargins` が全体をまとめて戻す。
- どの枠も、その外側にあるものから一定以上離れた位置に収まる。別の枠からは `groupGap`(10)、
  素のノードからはパディング 1 つ分多い 35 である。枠につながる junction ノードとの間も
  `groupGap` だけ空ける。押す量はマス単位に切り上げるので、縦に積まれたシーケンスは、枠の
  有無にかかわらず中心同士で 100px(メンバーの間に空きマス 3 つ)離れ、枠を消しても間隔が
  広く残ることはない。この離す処理は `settleCollisions` の役目である。各枠を中身ごと動かす
  ので、ワイヤで噛み合った 2 つの枠でも引き離せる。
- **下方向にしか**押さない。したがってこのパスは冪等である。すでに離れているキャンバスは
  何も動かさずに終わり、もう一度走らせてもずり下がらない。
- 水平方向に重なっているもの同士しか比較しない。横に並んだ 2 つのシーケンスが互いを
  押し下げることはない。

## junction ノードはつなぐ先に付いていく

junction ノードと link ノードはユーザーの配線の一部であり、レイアウトが置くものではない。
しかし 2 つの枠の間にユーザーが置いた junction ノードは、それが流れ込む先のフローに属している。
上の枠にノードが加わって下の枠が押し下げられたとき、junction ノードを元の場所に残すと
広がった枠の中に入り込み、下の枠の横にある `link in` は置き去りになる。

そこで、枠の外の junction ノードと link ノードは、**つなぐ先と一緒に動く**(`routingAnchors`)。
junction ノードと `link in` はその先のノードに、`link out` はそこへ送り込むノードに付いていく。
途中に別の junction ノードや link ノードがあれば、その先までたどる。先のない junction ノードは、
送り込む側に付いていく。

- ノードの配置パスのあと、もとからある junction ノードと link ノードは元の位置に戻し、
  **つなぐ先が動いた分だけずらす**。つなぐ先がそれぞれ違う量だけ動いた場合は置き場所が 1 つに
  決まらないので、元の位置に残す。1 つのシーケンスの中にある junction ノード(送り込む側と
  つなぐ先が同じ枠にあるか、どちらも枠の外)は、送り込む側の動きも数える。鎖がその junction
  ノードごと組み直されると両側の動きが食い違うので、元の位置に残る。つなぐ先の側だけに
  付いていくと、送り込む側のノードの上に乗ってしまうからである。
- `settleCollisions` と枠の整列は、つなぐ先がすべて動くとき、junction ノードと link ノードを
  その枠や鎖と一緒に動かす。衝突の判定でも、これらはつなぐ先の一部として扱うので、それだけが
  引き離されることはない。
- junction ノードをそれ自体の都合で動かすことは今もない。枠の中の junction ノードは、
  メンバーとして枠と一緒に動く。

## コメント配置

キャプションは「何に接しているか」で見つける。その許容範囲はわざと狭くしてあり、独立した
注釈はどのノードにも紐づかず、ユーザーが置いた場所に残る。**ただし、同じ枠に入っている場合は
この判定より優先する。** キャプションとその下のノードが同じグループのメンバーなら、横方向に
少しでも重なっていれば紐づける。スキーマが 2 つを 1 つの枠に入れ、エディタが 1 本の枠線で囲んで
いる以上、それは「同じ列にいるかどうか」より強い、「一緒のものである」という主張だからである。
これがないと、列から少しずれたキャプションはノードが動いた瞬間に取り残され、再配置のたびに
置き去りになっていた。枠のほうも、メンバーであるキャプションを他のメンバーと同じように数える
ので、`fitGroups` はキャプションまで含めて枠を合わせる。

ここから 2 つの規則が出てくる。どちらも「枠の境界」の話である。

- **探索は境界を越えない。** 枠の中のキャプションが見出すのは、必ず同じ枠の中のノードである。
  あるシーケンスの末尾にあるキャプションは、次のシーケンスの先頭と「接している」距離に入って
  しまう。そこで境界を越えて紐づけると、2 つのグループが 1 つのブロックにまとまってしまう。
  ブロックは自分自身と引き離せないので、橋渡ししたキャプションの高さぶん、枠同士が重なる。
- **どこにも接していない枠の中のキャプションは、置き直す。** その枠の(読み順で)最初の
  メンバーの上へ積む。キャプションはそのシーケンスの見出しであり、メンバーだけを動かす
  レイアウト処理は、見出しを「自分が名指しした行より下」に置き去りにしうる。そこでは何にも
  接しておらず、後続のどのパスも二度と見つけられない。

各コメントは、対象のキャンバスノードの直上に配置される。

- **縦方向**: 対象の上端に**グリッドギャップなし**で接する(中心間の差 = `nodeHeight` = 30px)。
- **横方向**: コメントの**左端**が対象の左端に一致する
  (`commentX = target.leftEdge + commentWidth / 2`)。これにより、幅の広いキャプションが
  対象の狭い中心に中央揃えされることなく、見出すノードと同じ列に座る。

対象ノードは、コメントごとに次の順で選ぶ。

1. **明示的な指定** — スキーマがコメントの貼り付け先ノードを名前で指定している場合。インポート側が
   その名前を実ノード ID へ解決し、レイアウトはそれをそのまま使う。指定先は、同じスキーマ内の
   新規ノードでも、すでにキャンバスにある既存ノードでもよい。
2. **フォールバック** — 貼り付け先の指定がないコメントについては、変換時に記録しておいた宣言順を
   使い、そのコメントの次に現れるキャンバスノードを対象とみなす。

同じノードを対象とする複数のコメントは、互いに接するように上へ積み上がる。積み上げの際は、
すでにキャンバス上でその対象の直上にある**既存の**コメントも数に入れる。新しいコメントが既存の
積み重ねに重ならず、その上に乗るようにするためである。

**貼り付け先の指定がない末尾のコメントは落とされる。** 変換の段階で、指定がなく、かつ宣言順で
後ろにキャンバスノードもないコメントを取り除いているので、レイアウトに届く時点ではすべての
コメントが解決可能な対象を持っていることが保証される。貼り付け先を指定したコメントは、スキーマの
どこに書かれていても保持される。

## 各パスの詳細

### `layoutNodes` — トポロジカル位置

1. **コンポーネント分け** — 接続を向きなしとみなして幅優先探索し、繋がったノードのかたまりを求める。
2. **列** — 各かたまりの起点から接続の向きに沿って幅優先探索し、1 つ進むごとに列を 1 つ増やす。
3. **行** — 最初の列は上から順に並べる。以降の列は「親たちの行の平均」を目標にし、そこが埋まって
   いれば空いている行が見つかるまで 1 つずつずらす。
4. **積み上げ** — かたまり同士は行番号の上で隙間なく詰めておき、実際のピクセル間隔は後段で与える。

### `reflowCanvasNodes` — 全体レイアウト

1. キャンバス上の実体だけを残して絞り込む。
2. 各ノードの接続配列から、前後の隣接関係を組み立てる。
3. トポロジカルな位置(列・行・所属するかたまり)を求める。
4. **左端を親から決める** — 各かたまりを列の順に、親を先に処理しながらたどる。各ノードは、
   すでに置かれた親があれば「親たちの右端の最大値 + 横の余白」を左端にし、親がなければ
   キャンバスの開始位置を左端にする。
   - どのかたまりでも列 0 のノードは同じ開始位置を共有するので、各フローの先頭ノードが左端に揃う。
   - 同じ親から枝分かれした兄弟は、その親の右端に余白を足した同じ左端を共有するので、これも揃う。
   - 鎖の下流ノードは**その鎖自身の**幅だけで進んでいくので、並行する別のフローに幅広のラベルが
     あっても、こちらの鎖が右へ引きずられることはない。
   - そのあと最後の列から順に、各ノードを、つながる先のうち最も近いノードの手前に横の余白
     ちょうどが空くまで右へ寄せる(左へは動かさない)。幅の違う 2 つの入力が 1 つのノードに入る
     場合も、どちらも余白ちょうどで手前に並ぶ。狭いほうは右揃えになり、その場合は列 0 の
     ノードが同じ開始位置を共有しなくなる。どのワイヤも横の余白ちょうどの長さになる。
5. かたまり同士を、指定した縦の余白以上に縁と縁を空けて積み上げる(ステップをマス目の倍数に切り上げる)。
6. 各ノードの中心座標を「左端 + 幅の半分」、縦位置を「行番号 × 行ピッチ + 所属かたまりの縦オフセット」
   として確定する。
7. 最後に、先頭に置かれるコメントを対象ノードの上へ配置し直す。

#### 具体例: 幅の異なる並行フロー

`edgeGap = 40`, `spacingY = 40`, `componentGap = 60`, `startX = 200`, `startY = 200`。
Flow A は幅広ラベル、Flow B は狭い。

| Node | width | leftEdge | x (centre) | y |
|------|------:|---------:|----------:|--:|
| `a1` (inject, "Sensor")                | 120 | 200 | 260 | 220 |
| `a2` (function, "Compute aggregated…") | 320 | 360 | 520 | 220 |
| `a3` (debug)                           | 120 | 720 | 780 | 220 |
| `b1` (inject)                          | 120 | 200 | 260 | 320 |
| `b2` (function, "fn")                  | 100 | 360 | 410 | 320 |
| `b3` (debug)                           | 120 | 500 | 560 | 320 |

`b3` は leftEdge 720 ではなく 500(= 360 + 100 + 40)に着地する。Flow A ではなく Flow B 自身の
幅に従うからである。`a1` と `b1` は leftEdge 200 を共有し、`a2` と `b2` は leftEdge 360 を共有する
(どちらもデフォルト幅の inject の下流)。より深い列では分岐する。最初の行の中心は `200 + 15` を
切り上げた 220。Flow B はかたまり 1 ステップ分(`30 + 60` を切り上げて 100)下にあるので、
Flow A の下端(235)と Flow B の上端(305)の縦ギャップは 70px になる。

### `placeAddedNodesNearNeighbors` — 増分レイアウト

`rightEdge(p) = p.x + width(p)/2`、`leftEdge(s) = s.x - width(s)/2`。

| Step | 内容 |
|------|--------------|
| 1 | 既存ノードを、編集前に保存しておいた座標へ戻す。 |
| 2 | キャンバス上の実体すべてから、前後の隣接関係を組み立てる。 |
| 3 | 新規ノードを、すでに置かれている隣接ノードの脇へ順に置く。前も後ろも繋がっていれば、前のノード群の右端に余白を足した位置に置き、縦は前後の平均の中間に最も近いマス目の線にする。前だけなら前のノードの右上、後ろだけなら後ろのノードの左上に置く。 |
| 3.4 | 新規ノードと、その後ろに繋がる既存ノードの組を見て、新規ノードの右端＋余白が既存ノードの左端を越えていたら、その既存ノードから接続の向きに沿って前方へたどり、届いた各ノードを必要な分だけ右へずらす。経路が合流する場合はずらし量の大きい方を採る。ここで動かしたノードは記録しておき、後段の押し下げ判定へ渡す。 |
| 3.5a | **同じかたまりの中での押しのけ** — 新しく置いたノードが、**同じかたまりに属する**既存ノードと横に近すぎ、かつ縦もほぼ同じ高さにあるなら、行ピッチ 1 つ分だけ下へ押す。変化がなくなるまで繰り返す。別のかたまりとの衝突はここでは意図的に無視する(次の段で扱う)。 |
| 3.6 | **挿入したフローの組み直し** — 新規ノードをうまく既存の鎖に繋げられたかたまりについて、位置を固定したままそのかたまりだけを組み直す。現在の左上を保ったまま全体レイアウトを適用する。その結果、同じかたまりの中ではユーザーが置いた既存ノードも動く。挿入されたノードに幅を考慮した一定のリズムを与えるには、これしか方法がない。どこにも繋がらなかった新規ノードは対象外で、次の段でまとめて配置される。「接続したら必ず組み直す」という挙動はユーザーとの取り決めである。前段の安価な押しのけが先に走っているので、この段は常にまともな初期状態から始まる。 |
| 3.5b | **かたまり同士の押し下げ** — 現在の接続関係でノードをかたまりに分ける。新規ノードを含むか、直前の段で右へずらされたノードを含むかたまりを「変更済み」とみなす。変更済みのかたまりごとに、外形が縦横とも重なっていて、かつ上端がそれより下にある未変更のかたまりを集める。集めた全体に対して**一律の**下げ幅を 1 つだけ求め、同じ量だけまとめて下げる。下げ幅は「変更済みの下端＋帯の余白」から「集めた中で最も上にある上端」を引いた値をマス単位に切り上げたもので、外形は縁で測るので、少なくとも帯の余白が縁と縁のあいだに空く。**この段でコメントは動かさない。** コメントは後段で対象ノードに追随するか、独立しているならその場に留まる。押し下げられたかたまりは次の繰り返しで押す側にもなる(連鎖する)。完全に上側から始まっているかたまりは決して押されない。動かす向きは下だけである。 |
| 4 | どこにも繋がらなかった新規ノードは、すでに置かれた全ノードより下に、独立したグラフとして改めて配置する。この帯の最初の行は、直前のフローの下端との間に帯の余白以上の隙間が空く、マス目の上の位置に来る(前段の押し下げと同じ計算である)。横方向は、すでに置かれたノード群の**最も左の左端**(最も左の中心ではない)から始める。**コメントはこの帯には決して入れない。** キャプションは持ってきた座標のままか、最後のコメント配置でスキーマ指定の対象の上へ置かれる。 |
| 5 | **コメントの追随** — 元々キャンバスノード(またはその上に積まれた別のコメント)に*接していた*コメントを、そのノードの新しい位置へ、元の相対位置を保ったまま貼り直す。独立したコメント — 最も近い対象より明らかに下にあるか、その描画範囲から外れているもの — は追随させず、ユーザーが置いた場所に留める。 |
| 6 | **最後のコメント配置** — スキーマで新しく追加されたコメントと、応答が `above` を指定した既存のコメントを、解決済みの対象ノードの上に置く。帯に置かれたものも含め、すべての対象が最終座標を持ったあとに行う。 |

#### 保証: 未編集フローは平行移動のみ

追加されたノードも、横へずらされたノードも**含まない**かたまりは、組み直されることも形を崩される
こともなく、**剛体として一律に平行移動される**だけである。組み直しの対象になるのは、編集された
かたまりだけである(Step 3.6)。他のフローは、かたまり同士の押し下げ(Step 3.5b)で、つながった鎖ごと
丸ごと下へ動く。それでも残った重なりは、インポートの最後の `settleCollisions` が同じ方法で解消する。
これにより、隣接するフローに編集がたまたま重なっても、ユーザーが丁寧に配置したフローの形は
そのまま保たれ、単に隣が下へずれるだけになる。

#### 具体例

デフォルト名のノード(inject=120, function=140, debug=120)、`edgeGap = 40`:

| State | A (inject, 120) | N (function, 140) | B (debug, 120) |
|-------|---|---|---|
| Before | (100, 100) | — | (280, 100) |
| Step 3 | (100, 100) | (270, 100) ← leftEdge=200 | (280, 100) ← overlap |
| Step 3.4 | (100, 100) | (270, 100) | (440, 100) ← leftEdge=380 |

- `A→N: leftEdge(N) = A.rightEdge + 40 = 160 + 40 = 200`, `x(N) = 200 + 70 = 270`.
- `N→B (Step 3.4): leftEdge(B) = N.rightEdge + 40 = 340 + 40 = 380`, `x(B) = 380 + 60 = 440`.

幅広の N(ラベル "Compute aggregated rolling average" → 320px):

| State | A (inject, 120) | N (320) | B (debug, 120) |
|-------|---------|---------|---------|
| Step 3 | (100, 100) | (360, 100) ← leftEdge=200 | (280, 100) |
| Step 3.4 | (100, 100) | (360, 100) | (620, 100) ← leftEdge=560 |

コンポーネント間プッシュ(Step 3.5b)、`bandGap = 60`, `nodeHeight = 30`:

- Flow 1(コンポーネント M、編集済み): `A(100,100) → B(280,100) → C-new(460,100)`。
- Flow 2(コンポーネント O、未変更): `D(100,180) → E(280,180)`。

このとき:

- `M.bbox = {x:[40, 520], y:[85, 115]}`, `O.bbox = {x:[40, 340], y:[165, 195]}`。
- bbox は横方向に重なる。`O.minY (165) > M.minY (85)`。縦方向の重なりなし → シフト不要。
  `D`/`E` は `y=180` に留まる。

ここで背の高いスタックを挿入して M が下方向に `y=200` まで伸びると:

- `M.bbox.maxY = 215`, `O.minY = 165` → `dy = 215 + 60 − 165 = 110`、切り上げて 120。
- `D`/`E` は両方 `+120` シフト → `y=300`。O の形状(内部の横レイアウト)は正確に保たれる。
