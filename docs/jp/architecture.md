# アーキテクチャ — ソース実装ガイド

LLM プラグインのサイドバーを支えるクライアント／サーバモジュールの技術リファレンス。

> **設計上の根拠 — 処理フロー・ルール・優先順位と「なぜそうなっているか」は
> [design.md](./design.md) にまとめてある。** 本ドキュメントは「各モジュールが何をするか」の
> カタログ、design.md は「なぜその順序・ルールなのか」を扱う。

## 全体像

```
Editor sidebar (vibe_ui)  ──Send──►  /llm-plugin/generate  ──►  Ollama / OpenAI / Custom
        ▲                                              │
        │                                              ▼
   addMessageToUI                          response { response, model, elapsed }
   importFlowFromMessage  ◄──────────────────────────────┘
        │
        ├── extractFlowNodes  (LLMJsonParser → Vibe Schema → FlowConverterCore.toNodeRed)
        ├── rebuildWorkspaceFromSnapshot (additive wires + property preservation
        │                                 + CanvasLayout positions x / y)
        └── replaceWorkspaceFlow → RED.nodes.import (canvas already laid out)
```

`src/core/` にある3つの独立したコアモジュールが、変換＋レイアウトの土台を形成する:

| モジュール | 担当 | 参照 |
|--------|------|-----------|
| `flow_converter_core.js` | Vibe Schema ↔ Node-RED JSON + 型判定ヘルパー | [vibe-schema.md](./vibe-schema.md) |
| `canvas_layout.js` | トポロジカルレイアウト、幅を考慮した間隔、コメント配置 | [layout.md](./layout.md) |
| `llm_json_parser.js` | JSON 修復、fuzzy エイリアス一致、スキーマ抽出 | (インライン JSDoc) |

残りはすべてプラグイン固有のグルーコード。まず下のファイルマップを見て、
各ファイルの詳細はモジュールリファレンスを参照。

## 読み込み順(クライアント)

`llm_plugin.html` が `<script src="llm-plugin/src/client.js">` を読み込み、
残りを**順番に**取得・実行する:

```
common → canvas_layout → flow_converter_core → llm_json_parser
       → chat_manager → importer → ui_core → vibe_ui
```

レイアウトエンジンは変換器より前でなければならない。変換器がノードの座標決めを
レイアウトエンジンに任せているためである。全モジュールは即時実行関数で自身を包み、
共通のグローバル名前空間を介して互いを参照する。

## モジュールリファレンス

### `client.js`

スクリプトを順番に読み込むローダーと、設定ダイアログのコントローラを兼ねる。
コントローラは HTML 側のフォームテンプレートに結びつき、「設定を読み込む」「設定を
書き出す」の2つの操作を外に見せる。プロバイダの切り替え、API キーのマスク表示、
最大プロンプト長(100–100,000)の扱いはここが受け持つ。

### `common.js`

全モジュールが使う小さな共有ヘルパー群。HTML と正規表現のエスケープ、エディタが
利用可能かを確認してから出すトースト通知、要素生成のショートハンド、ランダム ID の
発番、ワークスペース ID からタブ名への変換。

### `core/flow_converter_core.js` — Vibe Schema 変換器

Vibe Schema と Node-RED の JSON を相互に変換する。あわせて「そのノードは config
ノードか」「キャンバスに置ける実体か」「入力を持たない種類か」「出力を持たない種類か」
といった型判定と、エディタに登録済みの型情報を実行時に問い合わせる仕組みを提供する。
メタデータの約束もここが持つ: アンダースコア始まりのプロパティはプラグイン内部用であり、
LLM へ出力もせず、LLM からも受け付けない。
プラグイン外からも単体で読み込める形式で書かれている。
[vibe-schema.md](./vibe-schema.md) を参照。

### `core/canvas_layout.js` — レイアウトエンジン

ノードの座標決め専用。プラグインの他の部分に一切依存せず、単体で読み込める。
[layout.md](./layout.md) を参照。

### `core/llm_json_parser.js` — LLM 出力パーサ

LLM の JSON 出力の癖を許容するための層。コメントの除去、壊れたクォートの修復、
表記ゆれを許すエイリアス照合、散文混じりの応答からのスキーマ抽出を行う。

| エクスポート | 用途 |
|----------|-----------|
| スキーマ抽出 | `extractVibeSchema`, `extractConnectionHints`, `extractFlowDirectives` |
| フロールックアップ | `buildFlowLookup`(エイリアス / 名前 / ID のいずれからでもノード ID を引く。完全一致で見つからなければ表記ゆれを許す照合に落とす) |
| ノード抽出 | `extractFlowNodes` |
| 診断 | `diagnoseJsonExtractionFailure` — ノード抽出が何も返さなかったとき、各コードフェンスを改めてパースし直し、最初に見つかった具体的なパースエラーを行・列・該当箇所付きで返す。これによりインポート側は漠然とした「JSON が見つからない」ではなく「何行目で構文が壊れている」と表示できる。 |

トークン正規化、JSON 修復(コメント除去・クォート修復・釣り合いの取れたスニペットの走査)、Agent の部分スキーママージは、上記 4 つのエントリポイントの
内部ステップであり、エクスポートしていない。

### `chat_manager.js`

チャットセッションのライフサイクル。

| API | 説明 |
|-----|-------------|
| `getCurrentChatId()` / `getChatHistory()` / `startNewChat()` | メモリ内のセッション制御。 |
| `addMessage(content, isUser, meta?)` | メッセージを履歴に足し、サーバへ保存し、チャット欄に描画する。 |
| `saveChatToServer(chatId)` | 1チャット分をサーバへ保存。 |
| `loadChatHistoriesFromServer()` | 保存済みチャットを取得。まだ何も開いていなければ最新のものを自動で開く。 |
| `loadChat(chatId)` | 保存されたメッセージをチャット領域に再生する。 |
| `showChatList()` / `deleteChat(chatId, cb)` | チャット一覧モーダル。 |
| `saveImportCheckpoint(chatId?, flowIds?)` | インポート直前に対象フローを丸ごと控える。控えた時点をメッセージに紐付けておき、メッセージ横の Restore ボタンがそこまで巻き戻す。チャット送信のたびではなく、インポートボタンが押された時点で呼ばれる。控える範囲には junction と group も含める([design.md](./design.md#7-スナップショットの完全性と-junction--group)参照)。 |
| `updateMessageMeta(messageId, patch)` | 保存済みメッセージのメタデータをパッチ。 |

### `importer.js`

LLM 応答から Node-RED フロー JSON を抽出し、エディタへインポートする。

**`extractFlowNodes(messageContent, options?)`** —
応答中のコードフェンスを走査し、**最後の**有効なブロックを採用する。解釈は
Vibe Schema を最優先とし、それで読めなければ生の Node-RED 配列、さらにコードフェンスの
外に裸で書かれた JSON へと順に落とす。コメント除去は文字列リテラルを避けて行うので、
function ノードのコード中に書かれた `//` は消えない。Agent モードのときは、LLM が返した
部分的なスキーマを現在のフローに重ねてから解釈する。こうしないと、応答が言及していない
既存ノードを接続の相手として指定できないためである。

**`importFlowFromMessage(messageContent, options)`** —
以下を保証する完全なインポートワークフロー:

1. **マージセマンティクス** — すべてのインポートは列挙されたノードを追加/更新し、
   `null` にマップされたエイリアスを削除し、言及されないものはそのまま残す。
   適用方法はマージのみ — 別の方法を選ぶフィールドはスキーマに存在しない — なので、
   1つのスキーマで追加・更新・削除を自由に組み合わせられる。
2. **ワークスペースのスコープ** — その回の会話で LLM にコンテキストとして渡した
   フローだけを書き換え対象とする。サイドバーがメッセージに記録しておいた対象フロー
   一覧をインポート処理に渡し、「どのタブへ書くか」を決めるすべての判断がその範囲に
   閉じる。タブ名の解決も、後述の暗黙のフロー推定も、複数フローへの振り分けも、
   範囲外のタブは最初から候補に入れない。アクティブタブが範囲外なら、アクティブタブ
   ではなくコンテキストフローを対象にする。そして実際に置き換えを実行する直前に
   最終確認を行い、対象が範囲外ならインポートそのものを中止する。
   これは体裁ではなく正しさの要件である: 自動生成されるエイリアスはフロー**内**でしか
   一意ではなく、置き換えは対象キャンバスをいったん消してから作り直すため、範囲を
   絞らないと、会話が一度も見ていないフローを破壊的に書き換えうる。さらにチェックポイントは
   コンテキストフローの範囲でしか控えていないので、Restore でも戻せない。
   コンテキストを1つも選んでいない場合は「範囲指定なし」とみなし、従来どおり
   アクティブタブを対象とする。リグレッションテスト: `test/cross_flow_isolation.test.js`。
3. **暗黙のフロー推定** — どのタブに置くかの指定をスキーマが省略していても、そのノードや
   接続がコンテキストフロー上の既存ノードを指しているなら、そこから所属タブを割り出す
   (会話が「MCU 側 / Server 側」のように複数タブにまたがるとき、LLM はこの指定を落としがち)。
   コンテキストフローのキャンバスを走査して「このエイリアスはどのタブのものか」を作り、
   既存ノードと名前が一致するスキーマ上のノードにその所属を与え、さらに接続をたどって
   隣接する新規ノードにも所属を伝播させる。こうして補われたスキーマをフローごとに
   振り分けるので、明示的な指定がなくても複数フローへの適用が働く。
4. **厳密な 削除 → 追加/更新 → 接続 の順序** —
   再構築は3つの段階を明示的に分けて実行し、1つのスキーマがマージの途中で
   自己矛盾しないようにする:
   - *第1段階(削除)* は削除指示で名指しされたノードを、控えておいた元のフローから落とす。
   - *第2段階(追加/更新)* は残りの提案をノード ID ごとにマージする。このとき、第1段階で
     消したばかりのノードは、ID でもエイリアスでも復活させない。
   - *第3段階(接続)* は「既存ノードの自動エイリアス・新規ノードが名乗るエイリアス・
     ノード名・ID」をすべて引ける1つの索引を作り、行き先を失ったワイヤを掃除し、
     切断指示を適用したうえで、同じ索引を使ってスキーマの接続を張る。索引が1つなので、
     Ask / Agent どちらのモードが生成した応答でも新規ノードのエイリアスが解決できる。
5. **加算的なワイヤマージ** — 提案されたノードが既存ノードと一致した場合、接続先は
   出力ポート単位で既存の接続先と足し合わせる。接続が切られるのは、明示的な切断指示が
   あったときだけである。
6. **プロパティ保存** — LLM が言及しなかったプロパティは既存ノードの値のまま残す。
   「言及した」の判定には、スキーマ上で実際に書かれたキーの一覧を使う(生の JSON 経路では
   値が入っているキー)。これにより、変換時に補われる既定値がユーザーの設定を
   上書きしてしまうことがない。
7. **コメント配置** — すべてのコメントは対象キャンバスノードを `above: <alias>` で
   指定し、そのノードの直上にグリッドギャップ 0 で配置され、**左端が**対象の左端
   (中心ではなく)に揃う。新しいコメントは同じ対象に接している既存コメントの上に
   スタックし、重ならない。`above` を持つコメントは宣言順に関わらず保持される —
   `above` がなく、リスト内に後続のキャンバスノードもないコメントだけが落とされる。
   `above` を省略したスキーマは「宣言順で次のキャンバスノード」にフォールバック
   する。[layout.md](./layout.md#コメント配置)を参照。
8. **Config Node 保護** — LLM は config ノードを作成も削除もできない。既存のものを
   エイリアスで参照するだけである。
9. **junction / group の保存** — 再構築のために控える範囲には、そのタブの junction と
   group も含める。含めないと、いったん全部消してから作り直す過程で失われ、junction 宛の
   ワイヤも「行き先のない接続」として掃除されてしまう。
   [design.md](./design.md#7-スナップショットの完全性と-junction--group)を参照。
10. **ID を変えない再配置** — 再配置指示
   ([vibe-schema.md](./vibe-schema.md#reposition-ディレクティブ)参照)は、名指しされた
   ノードだけを、ID・プロパティ・接続を保ったまま並べ直す。並べ直した一群は元の左上位置に
   固定し直すので、キャンバスの他の部分は見た目に動かない。
11. **メタデータの掃引** — 変換時に付けたアンダースコア始まりのプロパティは、キャンバスへ
   渡る前にすべて剥がす。1回目はマージ直後で、このときレイアウトがまだ必要とする
   並び順と配置先の情報だけを残す。2回目はレイアウト完了後で、残りも落とす。
   プラグイン内部の目印がフローに残ることはない。
   [design.md](./design.md) §0.1 を参照。
12. 以上を終えてから、対象のワークスペースをまとめて置き換える。座標はレイアウト
   エンジンに委ねる。

**`restoreCheckpoint(checkpointId)`** — 控えておいた時点を読み込み、ワークスペースの
フローを置き換える。このとき描画をひと呼吸遅らせる。そうしないと「ワイヤだけ描かれて
ノードの中身が空白のまま」になる描画競合が起きるためである。

### `ui_core.js`

| API | 用途 |
|-----|---------|
| `addMessageToUI(content, isUser, showActions, messageMeta?)` | メッセージ本体と再送 / インポートのボタンを描画する。アシスタントの発言にはモード・モデル・所要秒数のバッジを添え、文中のノード名をクリック可能にする処理も併せて走らせる。 |
| `formatMessage(text)` | Markdown として描画する。その前に山カッコをエスケープし、生の HTML が混ざっても実行されないようにする。 |
| `annotateNodeReferences(rootEl, targetFlowIds?)` | 応答中のノード名をクリック可能にする2段構えの走査。**1段目**は、バッククォートで囲まれた語をノード ID に解決し、当たったものをジャンプ用の要素に差し替える(コードブロック内は対象外)。**2段目**は残りの地の文を走査し、既知のエイリアス(3文字以上)と完全一致する語を拾う。LLM がバッククォートを付け忘れた言及を救うためである。単純な名前も複合的な名前も対象になる。長い候補から順に、かつ単語境界付きで照合するので、長い名前がその一部と同じ短い名前に負けることはない。タブは対象外、config ノードは対象に含め、クリックすると設定ダイアログが開く。対象フローが渡された場合、エイリアスの索引は LLM が見たのとまったく同じエクスポートから作り直す。こうしないと、同種ノードが複数あるときの連番が別のノードを指してしまう。渡されなければキャンバス上の全ノードから作る。システムプロンプト側でも LLM にノード名をバッククォートで囲ませているので、実際には1段目が主経路になる。 |
| `focusCanvasNode(nodeId)` | Debug サイドバーと同じ操作感でノードを指し示す。そのノードのタブへ切り替え、ノードを一時的に光らせ、ビューポートを中央に寄せ、再描画をかけ、約 2.5 秒後に光らせるのをやめる。config ノードはキャンバス上に位置を持たないので、代わりに設定ダイアログを開く。すでに削除済みのノードなら、その旨を通知する。 |
| `reannotateAllAssistantMessages()` | チャット欄にある全アシスタントメッセージのノード名注釈を貼り直す。エディタのフロー読み込み完了・デプロイ・タブ切替・ノードの追加/削除/変更に反応するよう一度だけ登録し、連続発火は 200 ミリ秒まとめる。サイドパネルがフロー読み込みより先にチャット履歴を描いてしまう起動直後の競合を解消し、その後ユーザーが編集やデプロイをしても注釈を追随させる。 |
| `createRestoreCheckpointButton(checkpointId)` | 共通の Restore ボタン。インポートのきっかけとなったアシスタントメッセージの上に差し込まれ、1クリックで編集前の状態まで巻き戻す。 |
| `getFlowsByIds(flowIds, opts?)` / `getCurrentFlow(flowIds?, opts?)` | 指定したタブと、そこから参照されている config ノードをエクスポートする。エディタ標準のエクスポート機能を通すので認証情報は落ちる。オプションを付けるとそのタブの junction と group も加える。これを使うのは再構築とチェックポイントの経路だけで、LLM に渡すコンテキストでは使わない。モデルが見るエイリアスの採番を変えないためである。[design.md](./design.md#7-スナップショットの完全性と-junction--group)を参照。 |
| `getActiveWorkspaceId()` / `extractWorkspaceIds(nodes)` | ワークスペース ID を求める小さなヘルパー。 |
| `retryLastUserMessage(messageMeta?)` | 再送対象のメッセージに控えた時点が紐付いていればそこまで戻してから、直前のユーザープロンプトを送り直す。こうしないと、次のリクエストが「すでに編集が当たった後のフロー」を見てしまう。控えがなければ、単に送り直すだけにする。 |

### `vibe_ui.js`

サイドバー本体。HTML 側のサイドバーと設定ダイアログのテンプレートから画面を組み立て、
続いて各操作を配線する:

- 送信 / 停止のトグル。1つのクリックハンドラが状態を見て振る舞いを変え、Ctrl+Enter で
  二重に発火しないようガードする。
- 送信中のリクエストは中断できる。停止を押すと実際に通信を打ち切る。
- **モードの見え方**: 切り替えたときにトーストで知らせ、リクエスト中は切り替えを無効化する。
  各応答の所要時間の行に、その回のモードをバッジで残す。
- **フローセレクタ**: フローの追加・変更・削除とタブ切替を購読し、消えたフローの選択を
  取り除く。アクティブなタブだけを選んでいるときは *Current Open Flow* と表示する。
- **セッション設定**(ブラウザのローカルストレージ): モデル名、モードの選択、フローの選択を
  サイドバー初期化時に復元し、ユーザーが変更したら保存する。すでに存在しないフローの選択は、
  ワークスペース側のイベントが来たときに遅れて取り除く。読み込みはいずれも例外を握りつぶし、
  ストレージが使えない環境では黙って既定値に戻る。
- **チャット履歴のたどり**: プロンプト入力欄で上下矢印を押すと、そのチャットの過去の
  ユーザーメッセージをシェルのように遡れる。手入力を始めた時点でたどりは解除される。
- 設定ダイアログ: フォーカス管理、Escape キー、背景クリックで閉じる。

エディタのサイドバー API が使えるようになるまでポーリングしてから、タブを登録する。

### `llm_core.js` — 共有 LLM エンジン

サイドバーの HTTP 層とランタイムノードの両方が使う、状態を持たないエンジン。ここに
集約しているからこそ、ランタイムノードはサイドバーでユーザーが設定したプロバイダや
API キーをそのまま引き継げる — 設定と認証情報の置き場は1つしかない。

| セクション | 主要関数 |
|---------|---------------|
| ストレージ解決 | `chatsDir` / `checkpointsDir` / `clientEventsLog` / `persistenceEnabled`(ユーザーディレクトリ → 一時ディレクトリ → メモリの順で、最初に書き込める場所を採用)、`writeFileAtomic` |
| 設定 + 認証情報 | `getPluginSettings`, `savePluginSettings`、暗号化した認証情報ファイル、旧形式のキーの移行、`maskApiKey`, `redactSecrets` |
| プロンプト構築 | `buildMessages`(システムプロンプトの読み込みと、現在のフローの Vibe Schema 化)、`buildChatMessages`(フロー文脈を伴わない素のチャット) |
| LLM アダプタ | `generateWithProvider(provider, settings, model, messages, {timeoutMs})` — 実際の送信先は Ollama のチャット API か、OpenAI 互換のエンドポイント。後者は接続先を指定しなければ OpenAI 本体、指定すれば llama.cpp / LM Studio / vLLM / LocalAI といったローカルサーバになる |

### `node/` — ランタイムワークフローノード

`llm-request` ノード(および Admin API ヘルパー)はこのエンジンを再利用する。詳細は
**[runtime-node.md](./runtime-node.md)** に別途記載。補足: サイドバーのチャット履歴は
対象フローの ID だけでなく**名前**も保持する。後から見返したときに、その回がどのフローに
対する対話だったかが読んで分かるようにするためである。

プロンプト組み立て:

```
messages[0] = {
  role: "system",
  content: <user system prompt (from settings), if set>
           + <contents of prompt_system.txt>
           + optional "CURRENT FLOW (Vibe Schema): ..."
}
messages[1] = { role: "user", content: <user prompt> }
```

チャット履歴は送らない — 各リクエストは LLM に対してステートレス。

#### セキュリティ対策

- **認証。** データを読む・書く・課金が発生する全エンドポイントは
  `RED.auth.needsPermission` で保護する(GET 2本は `llm-plugin.read`、
  残りは `llm-plugin.write`)。クライアント側は `Common.apiFetch` 経由で
  エディタのベアラートークンを付けて呼ぶ。これは明示的に書く必要がある。
  Node-RED は、プラグインが `RED.httpAdmin` に後から登録したルートには
  `adminAuth` を**自動適用しない**。コアの管理 API が自分のルートに個別に
  `needsPermission` を付けているだけで、後から足したものは同じことをしない限り
  素通しになる。`adminAuth` が未設定なら `needsPermission` は何もしないので、
  単独利用の環境の挙動は従来どおり。
  静的アセットの3ルート(marked.js、スタイルシート、`src/*`)は未認証のまま残す。
  `<script>` / `<link>` タグはヘッダを送れないためである。これらが配るのは
  プラグイン自身の公開済みクライアントコードだけで、`src/*` は `.js` / `.css` /
  `.json` に限定する。
- API キー(OpenAI と Custom エンドポイント)は AES-256-GCM で暗号化し
  (鍵は Node-RED の credentialSecret または自動生成したもの)、プラグイン専用の
  ファイルに保存する。フローの認証情報ファイルではなく自前のファイルに置くのは、
  デプロイ時の認証情報クリーンアップに巻き込まれて消されないようにするため。
  Node-RED 本体が `flows_cred.json` に使う CTR ではなく GCM を使うのは、CTR には
  改ざん検知がなく、書き換えられたファイルがエラーにならないまま攻撃者の意図した
  ビット列に復号されてしまうからである。GCM ならその時点で失敗する。
  旧 CTR 形式のデータも引き続き読める(`g1:` 始まりが GCM の目印)。次回の保存で
  新形式に書き換わる。旧バージョンが平文で保存していたキーは初回起動時に自動移行する。
- API キーはクライアントに返さず、マスクした形だけを返す。設定の書き込みは受け付ける
  フィールドを列挙方式で限定し、想定外のフィールドの注入を防ぐ。保存済みのキーは
  接続先の変更をまたいで引き継がない。`__EXISTING_KEY__`(保存済みのキーを使う指示)を
  送りながら同じリクエストで `customBaseUrl` を変更した場合は拒否する。そうしないと、
  クライアントからは読めないはずのキーを任意の送信先へ向け直す手段として設定フォームが
  使えてしまう。接続先 URL は `http:` / `https:` に限定する。
- プロンプト長の上限はサーバ側で検査する(既定 10,000 文字、設定可能な範囲は 100–100,000)。
  あわせてフローコンテキストにも独立した 1MB の上限を設ける。両者は同じシステム
  メッセージに連結されるので、後者の上限がないと、中身を `currentFlow` に移すだけで
  前者の上限を回避できてしまう。
- 保存するデータには上限を設ける。チャット・チェックポイントは各 5MB、
  クライアントイベントログは 5MB でローテーション、チェックポイントは 200 件を超えたら
  古いものから削除する。
- ファイルを読み書きするルートでは、パス名をファイル名部分だけに切り詰めたうえで、
  想定ディレクトリ配下に収まっているかを確認し、パストラバーサルを防ぐ。
- エラーメッセージとクライアントログは、出力前に API キー・URL・IP を除去する。
  クライアントイベントログの `meta` についても、コンソール表示だけでなくファイルに
  書く内容から除去する。
- LLM へ送る前に、フローコンテキストから認証情報を取り除く。ランタイムノードは
  さらに範囲を絞り、選択したフローが実際に参照している config ノードだけを送る
  (参照は再帰的にたどる)。インスタンス内の全 config ノードは送らない。

#### Agent モードはモデルが書いたものをそのまま動かす

これは機能の性質であって不具合ではない。そのうえでプラグイン最大のリスクでもある。

- Agent モードはモデルの応答を**確認なしで**キャンバスに適用する。`Auto deploy` を
  有効にすると、そのまま即座にデプロイする。
- ノード種別の**許可リストは設けていない**。生成されたフローには `function` ノード
  (ランタイムプロセス内で動く任意の JavaScript)や `exec` ノード(任意のシェル
  コマンド)が含まれうる。モデルが作れるものを制限すると、このモードの意義そのものが
  失われるため、あえて制限していない。

したがって、モデルの出力を支配できる者は Node-RED ホストを支配できる。設定した LLM
エンドポイントは信頼できるインフラとして扱うこと。そして**信頼できないテキストを
Agent ノードに流し込まないこと** — `http in` のペイロード、外部から届く MQTT
メッセージ、スクレイピングしてきたページの中身など。`Auto deploy` が有効なら、それは
リモートの文字列からホスト上のコード実行までが一直線につながることを意味する。
`llm-self-feedback` サンプルが「使い捨てインスタンス用の開発者向けおもちゃ」なのは、
まさにこの理由による。

## 開発メモ

- クライアント側に **jQuery は使わない**。素の DOM 操作と標準の通信 API だけで書く。
- **モジュール間の受け渡し**は、1つのグローバル名前空間にぶら下げた各モジュールを介して行う。
- **チャットとチェックポイントの保存先**はサーバ側で、`llm_core.js` が決める
  (上記のストレージ解決)。プラグイン自身のインストール先には書き込まないので、
  そのディレクトリが読み取り専用になるサンドボックス型のクラウド Node-RED(enebular 等)
  にもそのまま入れられる。どこにも書き込めない場合はメモリのみに退避し、警告をログに出す。
- **システムプロンプト**は起動時にプラグインのインストール先から読み込む。読み込めない
  極端な環境では、コードに埋め込んだ最小限のプロンプトにフォールバックする。
- **設定の保存**: 秘匿でない項目は Node-RED 内部の設定ストアに置く。ここはエクスポートされる
  フローには含まれない。API キーは暗号化した認証情報の置き場に分離する(上記セキュリティ
  対策を参照)。Custom エンドポイントの API キーは、認証不要のサーバなら空欄でよい。
- **新しいエンドポイントを足すとき**は HTTP 層に追加し、Node-RED を再起動する。
- **新しいクライアントモジュールを足すとき**は `src/` にファイルを置き、ローダーの読み込み
  順の並びに加え、共通の名前空間に公開する。
