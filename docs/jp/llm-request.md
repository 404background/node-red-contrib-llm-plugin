# `llm-request` ノード

> **まだリリースには含めていない(実装予定)。** デバッグが十分でないため、公開
> パッケージではノードとして登録しておらず、パレットにも現れない。コードは
> すべてここにある(`node/llm-request/`、エディタ側は `src/agent_apply.js`)。
> 以下は、その仕組みと目指している動作の説明である。有効にするには
> `package.json` の `node-red.nodes` の記述を戻せばよい。

LLM Plugin のサイドバーと並んで登録されるノード(パレットカテゴリ **llm-plugin**)。
フローから LLM を呼び出せる。プロバイダ・モデル・
対象フローは `llm-request` ノードに設定し、API キーと URL は **LLM Plugin サイドバー**
(Settings)から継承する。

## `llm-request` ノードの設定

| フィールド | 説明 |
|-------|-------|
| Mode | **Ask** — `msg.payload` に応答。フローを選んでいる場合はそれを渡したうえで「説明する」ことを求める(提案はさせない)。何も選んでいなければ素のチャットとして扱う。**Agent** — フローを組み立て、開いているエディタにライブ適用する。 |
| Provider | Ollama / OpenAI / Custom。キー & URL はサイドバー由来。 |
| Model | フリーテキスト(例: `llama3.1`, `gpt-4o-mini`)。**必須**。`msg.model` でメッセージ単位に上書き。 |
| Flows | 複数選択(なし / 1つ / 複数)。**両モード**で LLM にコンテキストとして送られる。ノードを開くたびにリストが更新される。 |
| API URL | フローコンテキストを読むための Admin API ベース — 通常はエディタが配信される URL(スタンドアロン `http://localhost:1880`。埋め込み: `httpAdminRoot` ベース、例 `http://localhost:8000/red`)。文字列、**flow/global** コンテキスト変数、**msg** プロパティのいずれかを受け取る。空欄 = 自動検出(推奨。非 1880 ポートに埋め込まれても動く)。メッセージから URL を読むのは、この欄を `msg` 型にしたときだけである。ノードはその URL へ取得しに行くので、既定でメッセージの内容に行き先を決めさせてはならない。設定した URL が失敗した場合、ノードは警告付きで自動検出にフォールバックする。 |
| Timeout | 秒。デフォルト **3600**(1時間 — ローカル LLM は遅いことがある)。`0` = 無制限。`msg.timeout` でメッセージ単位に上書き。 |
| Auto deploy | **Agent 専用、開発者向け機能。** チェックすると、変更を適用した直後にエディタがデプロイする。実行するのはエディタ自身の Deploy 操作で、確認ダイアログを出さない形で呼ぶ。無人のループが確認待ちで止まらず、未保存状態も正しく解消されるためである。デプロイは非同期で進み、結果はエディタ自身のデプロイ通知が報告する。レビューの機会はない。エディタは1つだけ開くこと。デプロイ種別は Modified Nodes / Modified Flows を推奨。使い捨ての開発インスタンスでのみ使うこと。**セキュリティ上の注意:** レビューの機会がなく、ノード種別の制限もないため、生成された `function` / `exec` ノードはこのホスト上でそのまま動く。信頼できない入力で Agent モードの `llm-request` ノードを駆動しないこと。 |

**入力:** `payload`(プロンプト。文字列は改行を正規化、オブジェクトは JSON 文字列化)。
**出力:** `payload`(テキスト応答 — `JSON.parse` しないこと)、`llm`
(mode/provider/model/elapsed)、Agent モードでは `flow`
(`{ targetFlows, dispatchedToEditor }`)。

**ステータス:** リクエスト中は青ドット(経過秒を刻む)、成功時は緑 `done (…)` / `sent to editor`、
失敗時は赤 `error` / `timeout`。

## Agent モードが変更を適用する仕組み

`llm-request` ノードはランタイム側にいるので、ブラウザのキャンバスを直接編集できない。そこで
応答を Node-RED の通信チャネルへ流し、エディタ側はプラグイン自身の `src/agent_apply.js`
がそれを受け取って、プラグインのインポート処理に渡す。サイドバーとまったく同じ経路である。
エディタ側の処理をノードではなくプラグインに置いているのは、ノードを薄い呼び出し役に
保つためである。そこで必要になるものは、もともとすべてプラグインのものだからである。

- `llm-request` ノードの **Flows** で選んだフローは、そのまま「書き込んでよい範囲」として
  インポート処理に渡す。サイドバーが対象フローを渡すのと同じ扱いで、**モデルに渡したフロー
  だけが返答で書き換えられる**。何も選ばなければフローのコンテキスト自体を送らないので、
  これまでどおり開いているタブが対象になる。
  [docs/jp/architecture.md](./architecture.md) の `importer.js` の保証2を参照。
- プラグインが読み込まれた**エディタが開いている必要がある**。ヘッドレス実行にはキャンバスがない。
  複数開いていれば応答は全エディタに届くが、適用するのは最初に受け取ったエディタだけ
  (write 権限が必要)なので、二重に適用されることはない。
- `llm-request` ノード経由の操作は**チャット履歴には残らない**(サイドバーとの違い)。
  ただし元に戻せないわけではない。エディタは適用の直前に対象フローのチェックポイントを
  `node-apply` の印を付けて保存する。ノードのチェックポイントには Restore ボタンを
  ぶら下げるメッセージがないので、サイドバーの **Restore Points** ダイアログが
  その発見手段である。チェックポイントを保存できなかった場合も編集自体は適用され、
  その旨が通知に出る。デプロイ前にキャンバス上でレビューすること。エディタの取り消し
  操作も使える。
- **適用は順番待ちする。** 応答が返るのはモデル次第なので、自分の編集を適用してまだ
  デプロイしていない最中に届くこともある。未確定の変更の上にマージせず、そのデプロイを待つ
  — [design.md §13](./design.md) を参照。**自動デプロイ**が有効なら保留は自分で解除され、
  無効なら利用者がデプロイした時点で解除される。
- **自動デプロイは検証を飛ばす。** エディタ側は `core:deploy-flows` を、デプロイ処理の
  `skipValidation` フラグ付きで呼ぶ。確認ダイアログの Confirm ボタンが通るのと同じ経路である。
  これがないと、ワークスペースの**どこか**に未設定・未知のノードが1つあるだけでモーダルが出て、
  無人のループは永久に答えられなくなる。デプロイは非同期なので、結果を報告するのはノードでは
  なくエディタ自身のデプロイ通知である。
- 意図的に**「deploy」ノードは用意していない。** サーバ側のノードからエディタの Deploy ボタンは
  再現できない。デプロイの対象はブラウザ側が持っているエディタの状態であり、これは純粋に
  クライアント側のものだからである。Agent モードは編集をその場で反映するので、ユーザーが自分で
  デプロイする。あるいは `llm-request` ノードの **Auto deploy** をチェックすれば、エディタ側が
  反映直後にエディタ自身のデプロイ操作を呼ぶ。サーバ側の deploy ノードでは無理だったことが
  これで成立するのは、ブラウザ自身がデプロイしているからである。

## ファイル

`llm-request` ノードを構成するファイル:

```
node/
  lib/admin_api.js              フローを読み出す管理 API クライアント(接続先を自動検出)
  llm-request/llm-request.js    ランタイム側: msg からプロンプト、プロバイダ呼び出し、エディタへの送信
  llm-request/llm-request.html  エディタ側: 設定ダイアログとヘルプのみ
src/
  agent_apply.js                エディタ側の適用処理: 通信チャネルを購読して応答をフローへ反映する
```

設定・認証情報・プロバイダごとの呼び分け・プロンプト構築・フローコンテキストの選別・
秘匿情報の伏せ字化を担う共有 LLM エンジンは [`src/llm_core.js`](../../src/llm_core.js)
にあり、サイドバーと共用している。ノードが持つのはノードらしい部分だけである。
すなわち `msg` の受け取り、ステータス表示、タイムアウト、設定値である。

## 例

**Menu → Import → Examples**(または `examples/` の JSON ファイル)からインポート:

- `llm-nodes` — `llm-request` ノードの Ask と Agent を並べたもの(コアノードのみ)。Agent 行の
  編集は開いているエディタにライブ適用される。レビューして手動で Deploy する — 自動デプロイは
  一切なし。
- `llm-self-feedback` — **開発者向けサンプル**: HTTP in/request ノードと `llm-request` ノードで
  組む Agent + Auto deploy の自己フィードバックループ。5イテレーションでハードキャップ
  (各ループは LLM リクエスト1回とデプロイ1回を要する — キャップは絶対に外さない)。
  イテレーション1が別の対象タブに小さなデモフローを作り、以降のイテレーションがそれぞれ
  改善する。LLM が完成と判断して `END` と応答する
  (ループの `next loop URL` 関数がチェック)か、キャップに達するまで続く。実行前に **Modified Flows**
  デプロイタイプを選び、ループフロー自体がイテレーション途中で再起動されないようにする。インスタンスの
  HTTP API エンドポイントベースは change ノードで1回設定する(フロー変数 `apiBase`、デフォルト
  `http://127.0.0.1:1880`)— 埋め込みインスタンスではそこで編集する(例 `http://127.0.0.1:8000/api`)。
