# 設計ノート — 処理フロー・ルール・優先順位とその理由

このドキュメントは、LLM プラグインが「ユーザーの指示 → LLM の応答 → フローへの反映」をどういう
**順序・ルール・優先順位**で行うか、そして **なぜそう実装されているか(理由)** をまとめたものです。
実装を議論するための共通の土台として使うことを目的としています。

- モジュール別の「何をするか」のリファレンス → [architecture.md](./architecture.md)
- 中間表現(Vibe Schema)の仕様 → [vibe-schema.md](./vibe-schema.md)
- レイアウトエンジンの詳細 → [layout.md](./layout.md)

このノートはそれらと重複せず、**設計判断と優先順位の「なぜ」** に集中します。

---

## 0. 設計の柱(なぜこの形か)

| 判断 | 理由 |
|------|------|
| **決定論的な処理はコード、論理的な思考は LLM** | この切り分けが他のすべての柱の前提になっている。**一意に決まるもの**(ノード ID の生成と重複回避、座標、接続配列の組み立て、エイリアスの割り当て、junction / group の保全)は必ずコード側が担当する。**LLM に委ねるのは「ノード同士の論理的なつながり」と「ノード内の設定」だけ**。確率的な出力に決定論的な仕事をさせると、ID の重複・座標の破綻・ワイヤの取り違えという形で必ず失敗が表面化し、しかもその失敗は検証しづらい。逆に「この inject を 5 分周期にして debug につなぐ」といった文脈からの意味づけは、コードでは決められない。 |
| **中間表現「Vibe Schema」を挟む** | 上の切り分けを構造として強制するための境界。Node-RED の生の JSON はランダムな ID・座標・型ごとの内部配列を含み、LLM が安定して生成・編集できるものではない。「種類と名前から作った人間に読めるエイリアス」を鍵にし、座標を持たない表現へ抽象化することで、LLM は ID を発明できず、座標を気にする必要もなくなる。 |
| **アンダースコア始まりのプロパティ＝メタデータ、LLM には渡さない** | エイリアス・宣言順・コメントの貼り付け先といった「コード側から次の工程への申し送り」は、アンダースコアで始まるキーとしてノードに載せる。この命名規約ひとつに、境界の両方向を紐づけている(§0.1)。 |
| **適用は必ず「マージ」** | LLM は毎回フロー全体を返すわけではなく、部分編集の方が普通である。「列挙されたものだけ追加・更新、空を指定されたものは削除、言及がないものは現状維持」に固定しておけば、応答が不完全でも既存フローは壊れない。適用方法をモデルに選ばせる分岐は持たない。判断を誤ったときに、既存フローが壊れる側へ倒れるためである。 |
| **反映はエディタ側(ブラウザ)で行う** | サーバから管理 API 経由で書き戻すと、開いているエディタの未保存状態(編集中の印やハイライト)を消せず、ユーザーの手元と食い違う。だからブラウザ内から直接キャンバスへ反映する。サイドバーからでも Agent ノードからでも同じである。 |
| **破壊的変更の前に必ずチェックポイント** | 適用はワンクリックで元のフローを書き換えてしまう。だから適用の直前に、対象フローを丸ごとスナップショットとして保存し、メッセージ単位で「元に戻す」を可能にしておく。エディタ標準の操作履歴には積まず、プラグイン独自のスナップショットで巻き戻す。 |
| **スナップショットは「完全なフロー」でなければならない** | スナップショットは、マージの土台であると同時に、失敗したときに戻す先でもある。さらにフォールバック時の適用は今でも対象タブを消すので、スナップショットに入っていないキャンバス要素は消えてしまう。したがって junction と group も含める必要がある(§7)。 |

### 0.1 メタデータ境界(アンダースコア始まりのプロパティ)

判定は一箇所にまとめてある —「キー名がアンダースコアで始まるか」だけ。この1つの規約で
**往路と復路の両方**を縛る。

| 方向 | 規則 | 実装箇所 |
|------|------|----------|
| **往路(LLM へ)** | 中間表現へ変換する側は、アンダースコア始まりのキーを一切出力しない。ID・所属タブ・座標・接続配列・所属グループも同様に落とす。結果としてモデルが受け取るのは **エイリアス・種類・名前・型ごとのプロパティ・接続だけ**になる。 | `flow_converter_core.js` `toIntermediate` |
| **復路(LLM から)** | Node-RED の形へ戻す側は、スキーマに書かれたアンダースコア始まりのキーを**無視する**(トップレベルでもプロパティの中でも)。メタデータを書けるのはこのモジュール自身だけで、モデルには偽装できない。自動生成した config の仮置きノードの印も、スキーマ上のフラグではなく変換中のローカルな記録として持つ。 | `flow_converter_core.js` `toNodeRed` |
| **キャンバスへ** | インポート側は2回に分けてメタデータを剥がす。1回目はマージ完了直後で、このときレイアウトがまだ必要とする並び順と貼り付け先の情報だけを残す。2回目はレイアウト後で、残りも落とす。**キャンバスへ渡る時点でアンダースコア始まりのキーはゼロになる。** | `importer.js` `rebuildWorkspaceFromSnapshot` |

- **理由**: 個別のキー名を名指しで消して回る方式だと、メタデータを1つ増やすたびに削除漏れが
  起きる(実際、コメントの貼り付け先を示す印がレイアウトに使われたあと、そのままキャンバスへ
  流れていたことがある)。命名規約でまとめて除外する形にすれば、新しいメタデータを足しても境界は
  自動的に守られる。
- **モデルが偽装できないことも規約の一部である**: たとえば「LLM がどのキーに言及したか」の記録
  (§4.2 のプロパティ保存の判断に使う)や「自動生成した仮置きノードである」という印(§5 の
  config 保護に効く)をスキーマから書けてしまうと、マージ規則そのものを LLM の出力で
  曲げられてしまう。
- 回帰テスト: `test/schema_conventions.test.js`(`npm test` に登録)。

## 1. データフロー(全体像)

```
ユーザー入力
   │  (モード = Ask / Agent、対象フローの選択)
   ▼
サイドバー ──送信──► HTTP 層 ─► 共有 LLM エンジン ─► Ollama / OpenAI / Custom
   │                                    │
   │   ┌── LLM へ渡すコンテキスト: 選択したフローを取り出し、中間表現へ変換
   │   │   （junction / group は含めない ＝ モデルが見るエイリアスの割り当てを変えない）
   ▼   ▼
応答テキスト（説明 + 必要なら Vibe Schema のコードブロック）
   │
   ├─ Ask  : ユーザーが「Import」ボタンを押したら適用
   └─ Agent: 応答を受け取った時点で自動的に適用
   │
   ▼
応答からフローへ反映する処理   ← 適用の中枢
   │
   ├─ 0) 適用直前のフローをスナップショットに保存（ボタンが押された時点で実行）
   ├─ 1) 対象タブの決定 — 書き込み範囲の限定と、暗黙のフロー指定の補完（§6）
   ├─ 2) 応答の解析 — ノード・接続のヒント・削除や再配置の指示を取り出す
   ├─ 3) 対象タブの現状を取得（junction / group を含めた完全な形で）
   ├─ 4) 削除 → 追加/更新 → 接続 の3段階で組み立て直す（§3）
   └─ 5) 組み立てた結果を「差分」として当てる（§12）
        └─ 差分で表現できない変更のときだけ、従来どおり対象タブを消して
           入れ直す方式にフォールバックする（§12）
```

Agent モードのランタイムノードも、応答をエディタへ送り、エディタ側で受け取った側が同じ適用処理を
呼ぶ。**適用ロジックはサイドバーと完全に共通である。**

## 2. Ask / Agent の違いと理由

| | Ask | Agent |
|--|-----|-------|
| 適用契機 | ユーザーが Import を押す | 応答受信後に自動 |
| 用途 | 内容を確認してから反映したい | 反復・自動化 |
| 共通点 | 適用ロジック・チェックポイント・マージ規則はすべて同じ | 同左 |

- **モードの違いは「いつ適用するか」だけ**にしてある。適用の中身を分岐させると片方だけ壊れるバグの
  温床になるため、適用処理はモードをほとんど見ない。唯一の例外は応答の解釈で、Agent のときだけ
  部分スキーマを現在のフローに重ねてから読む。

---

## 3. 適用の3段階（削除 → 追加/更新 → 接続）と、その順序の理由

再構築は必ず次の順で処理する。**順序そのものがルール**であり、1つのスキーマが自己矛盾していても
破綻しないための設計である。

### 第1段階: 削除
- 削除指示(エイリアスに空を指定したもの)で名指しされたノードを、スナップショットのフローから除く。
- 除いた ID を覚えておき、**第2段階が同じエイリアスを再び持ち込むのを禁じる**。
- **理由**: 「いったん消して作り直す」系の応答では、削除対象と同じ名前の新規ノードが同じスキーマに
  同居することがある。そのとき削除の意図を優先できる。

### 第2段階: 追加・更新
- 残ったフローをノード ID 引きにして、提案されたノードをマージする。
- **Config Node 保護**: 既存にない config ノードは追加しない(§5)。
- **ワイヤは足し算でマージする**: 既存ノードと一致した場合、既存の接続先と提案された接続先を
  出力ポート単位で足し合わせる。**接続を切るのは明示的な切断指示だけ**(§4)。
- **プロパティ保存**: LLM が触れていないキーは既存の値に戻す(§4)。

### 第3段階: 接続
- **1つに統合した索引**を作る(ここが肝心である):
  - 既存ノードの自動エイリアス、新規ノードが名乗るエイリアス、ノード名、ID を、すべて同じ索引から引く。
  - これがないと「既存の inject から新規の function へ」という接続で、送信元は解決できても送信先が
    解決できない。新規ノードは自動生成では単に種類名になり、LLM が付けた名前と一致しないためである。
- 存在しない ID 宛のワイヤを取り除き、切断指示を適用してから、スキーマの接続を張る。
- **なぜ接続を最後にするか**: 接続の両端は「削除も追加も済んだ最終的なノード集合」に対して解決しな
  ければならない。削除・追加より先に接続を確定すると、すでに消えたノードやまだ無いノードを指してしまう。

## 4. マージのルール（既存を壊さないための優先順位）

### 4.1 ワイヤ: 既定は「足す」、切るのは明示されたときだけ
- 既存の接続先と提案された接続先を、出力ポート単位で足し合わせ、重複は取り除く。
- 切断するのは、LLM が接続の削除を明示的に書いたときだけである。
- **理由**: LLM は編集対象ノードの接続を書き落としがちである。省略を「切断の意図」と解釈すると、
  無関係な既存接続まで勝手に消える。「接続が勝手に切られる」という不満を生まないための既定。

### 4.2 プロパティ: 「言及していないキーは既存のまま」
- LLM が明示的に設定したキーの集合をどう得るか:
  - Vibe Schema 経路では、変換の時点で「スキーマに実際に書かれていたキー」を記録しておく。
  - 生の JSON 経路では、値が入っているキーをそう見なす。
- それ以外のキーは、既存ノードの値に戻す。
- ただし同一性(ID・種類)、配置(所属タブ・座標・所属グループ)、接続、エディタの編集状態、および
  メタデータは引き継がない。これらは「プロパティ」ではなく、別のルールが決めるものだからである。
- **理由**: 変換時に型ごとの既定値(たとえば debug ノードの出力対象の指定)が補われても、ユーザーが
  以前に設定した値を上書きしない。「触っていない設定は保持される」を保証するためである。

### 4.3 ノードの照合: 完全一致のみ、あいまい一致は使わない
- 提案されたノードを既存ノードに割り当てるときは、**エイリアスの完全一致だけ**で判定する。
- **理由**: LLM にはプロンプトで既存エイリアスをすべて渡してある。一致しないエイリアスは「新規に
  作りたい」という意図だと解釈できる。ここであいまい一致を許すと、新しく作りたい `inject_py_1` が
  既存の `inject` に前方一致してしまい、無関係なノードを黙って上書きする。**「取り違えて上書き」
  より「新規として追加」の方が安全である。**

## 5. Config Node 保護

- LLM は config ノード(ブローカー設定や実行環境設定など)を **作成も削除もできない**。既存のものを
  エイリアスで参照するだけである。これはプロンプトと適用側の両方で強制している。
- 同種の config ノードが1つしかない場合は、その既存のものを再利用する。同じ設定が二重にできるのを
  防ぐためである。
- **理由**: config ノードは認証情報や接続先といった「壊れると影響範囲が広い」共有資源である。LLM が
  勝手に作ったり消したりして他のフローを巻き込む事故を防ぐ。config ノードはすべてコンテキストに
  含めたうえで、「参照は自由、生成と削除は不可」という非対称なルールにしている。

## 6. マルチフロー / 暗黙のフロー指定

- スキーマのノードにどのタブのものかが書かれていれば、タブごとに分割して適用する。
- **暗黙の指定**: LLM がその指定を書き忘れても、スキーマ上のエイリアスや接続が複数タブの既存ノードと
  対応づけられる場合、「このエイリアスはどのタブのものか」を割り出し、接続をたどって新規ノードにも
  隣のノードの所属を継承させる。
- **理由**: 「MCU 側 / Server 側」のように複数タブにまたがる指示では、LLM はタブの指定を落としがちで
  ある。指定がないと接続がアクティブタブの境界を越えられず、「送信側のノードに何もつながらない」と
  いう症状になる。そこを推定で補う。

### 走査範囲はコンテキストフローに限定する（必須）

推定も、タブ名の解決も、複数フローへの振り分けも、**LLM にコンテキストとして渡したフロー**の中だけを
走査する。全ワークスペースを走査してはならない。

- **理由**: 自動生成されるエイリアスが一意なのは**フローの中だけ**であり、タブをまたげば普通に衝突する。
  「エイリアスはどのタブのものか」の対応づけは先に見つかった方が勝つので、全部を走査すると
  「タブバーで手前にあるだけの無関係なフロー」が同名のエイリアスを先取りし、編集がまるごとそちらへ飛ぶ。
  しかも適用は、マージ後の最終状態に含まれないものを**削除する**（フォールバック時は対象キャンバスを
  消してから作り直す）ため、対象を取り違えた場合の影響は追加では済まず、破壊的になる。さらにチェックポイントは
  コンテキストフローの範囲しか保存していないので、Restore でも戻せない。
- 範囲を絞ることで「書き込む範囲 ⊆ スナップショットに入っている範囲」が常に成り立ち、Restore が
  いつでも有効になる。
- アクティブタブが範囲外のとき(送信後にユーザーがタブを切り替えた場合など)は、アクティブタブではなく
  コンテキストフローを対象にする。範囲指定がない(フローを1つも選んでいない)ときだけ、従来どおり
  アクティブタブを対象とする。
- 実際に適用する直前の最終確認で、対象が範囲外なら**中止**する。
- リグレッションテスト: `test/cross_flow_isolation.test.js`(エイリアス衝突 / タブ切替 / 複数フローへの
  波及 / 範囲外のタブ指定 / 範囲指定なしのときの後方互換)。

## 7. スナップショットの完全性と junction / group

### 前提（Node-RED エディタの内部構造）
- タブを指定してノードを取り出すエディタの標準 API は、**通常ノードしか返さない**。junction と group は
  それぞれ別のレジストリで管理されており、専用の取得 API を呼ばないと手に入らない
  (Node-RED 4.1.7 のエディタクライアントで確認)。
- 復元処理と、差分適用がフォールバックしたときの適用は、対象タブの junction と group を**全部
  消してから**フローを入れ直す。したがって、スナップショットに入っていない要素はそのまま消える。
  さらに接続の段階で「作り直したフローに存在しない ID 宛」のワイヤは取り除かれるため、junction が
  スナップショットから欠けると、そこへ向かうワイヤまで行き先なしとして切られる。

### 設計（必要な場所だけが取り込む）
- フローを取り出す関数に「junction と group も含める」オプションを設け、有効にしたときだけ
  スナップショットに含める。エディタ標準のエクスポートは、junction を接続情報つきで正しく
  書き出してくれる。
- **フローを作り直す2箇所だけがこのオプションを使う**:
  - 適用時の再構築の土台を取るところ
  - チェックポイントを保存するところ
- **LLM に渡すコンテキストと、応答中のノード名注釈は、このオプションを使わない**。
  - **理由**: この2つは中間表現へ変換するときのエイリアスの割り当てを共有している。junction と group を
    混ぜると、モデルが見るエイリアスの並びが変わり、生成の挙動そのものが変わってしまう。
    **適用側だけが完全なフローを使い、生成側は従来どおり**にすることで、この不具合の修正が
    生成品質に影響しないよう切り分けた。

### レイアウトから group を外す理由
- junction は座標と接続を持つので、キャンバス上の実体として扱われる。実際に配線が通る点なので、
  レイアウトの隣接関係に含めてよい(位置は既存ノードの座標として保持される)。
- group も座標を持つため同じくキャンバス上の実体として扱われるが、**group の外形は自分のメンバーを
  囲むように決まる**。これを重なり解消の処理に渡すと「自分の中身と重なっている」と判定され、破綻する。
- そこで「キャンバス上の実体であり、かつ group ではないもの」という判定を別に設け、レイアウトの
  呼び出しにはこちらを使う。**group はレイアウトの対象から外し、位置は元のまま保つ。**
- 回帰テスト: `test/junction_preserve.test.js`(`npm test` に登録)。junction を挟んだ流れを編集し、
  junction 自体と前後両方向のワイヤが残ることを検証する。

### 巻き戻し用のバックアップにも同じ規則が効く
- どちらの適用方式も、ワークスペースに手を入れる前に自前のバックアップを取っておき、取り込みが
  失敗したときにフローを元へ戻す。このバックアップには**通常ノードしか入っていなかった**ため、
  「何も変えないはずの失敗経路」で junction と group だけが消えて戻らない、という状態に
  なっていた。
- バックアップに junction と group も含めるようにし、単純な JSON コピーではなくエディタ標準の
  エクスポートで作るようにした。エディタ上の group は、メンバーを**ノードの実体そのもの**として
  保持しているため、そのままコピーすると、取り込み側が ID の並びを期待している場所にノード全体が書き込まれてしまう。
- 回帰テスト: `test/import_safety.test.js` のシナリオ B。

## 8. レイアウトの優先順位（詳細は layout.md）

- **既存フローがある場合は差分配置**: 既存ノードの座標は編集前の位置に戻し、新規ノードだけを
  隣接ノードの右または左に置く。長い鎖の折り返しは無効にする(既存の形を保つため)。
- **完全な新規のときだけ全体再配置**: このときは長い鎖を折り返して収める。
- **間隔は「ノードの縁と縁のあいだの余白」**であり、中心間の距離ではない。ノード幅は、可能なら
  エディタが実測した値を使い、名前が変わって実測値が当てにならないときは推定値に切り替える。
- 再配置指示は名指しされた一群だけを並べ直し、元の左上位置に戻すので他は動かない。削除して作り直すと
  ID が変わってしまうため、ID を保ったまま整列し直せることに意味がある。

## 9. チェックポイント(巻き戻し)の考え方

- 適用の**直前**に対象フローをスナップショットに保存し、それを該当メッセージに紐付ける。
  メッセージ横の Restore ボタンがそこまで巻き戻す。
- **Agent ノードもチェックポイントを取る**(`saveNodeApplyCheckpoint`)。以前はノード経由の変更
  だけが「取り消せない唯一の経路」だった。しかもそれが一番効いてほしい場面ほど危ない。
  自動デプロイを有効にした無人のノードは、誰も見ていないところで動作中のランタイムに変更を
  入れてしまう。サイドバー用の関数は流用できない。チャットが存在しないからで、そのとき
  「たまたま開いているチャット」を流用すると、ノードの変更が無関係な会話の下に入り、その
  チャットを削除したときに一緒に消える。そこで `chatId` は null にし、`meta.source` を
  `node-apply` とする。あわせて `meta.node`(どのノードか)と `meta.targetFlowIds`
  (書き込みを許された範囲)も残す。チェックポイントの保存に失敗しても編集は中止しない。
  「復元ポイントを保存できなかった」旨を通知に出す。
- この2種類は**別々の上限**で整理する(`MAX_CHECKPOINT_FILES` / `MAX_NODE_CHECKPOINT_FILES`)。
  タイマー駆動のノードは起動のたびにチェックポイントを取るので、ディレクトリ全体を古い順に
  削る方式だと、その流量がサイドバーの Restore ボタンが指しているチャット側のチェックポイントを
  削除してしまう。ボタンは 404 を返し、復元できたはずのフローも残らない。種類ごとに枠を分けて
  おけば、頻繁に動作するノードが削除の対象にできるのは自分の分だけになる。
- ノード側のチェックポイントは紐付ける先のメッセージがないので、`GET /llm-plugin/checkpoints`
  で見出し情報だけ(フロー本体は含めない)を新しい順に一覧できる。`?source=node-apply` で
  絞り込める。**見つけられない復元ポイントは復元ポイントではない。** その画面が
  **Restore Points** ダイアログ(サイドバーのヘッダにある履歴ボタン)である。どちらが作った
  ものかのバッジ、何の直前に取ったものか、日時、スナップショットの規模、対象フローを並べる。
  対象フローは ID ではなく**フロー名**に解決して出す。「これが戻したい地点か」を判断する人に
  とって ID は何も意味しないからである。
- 整理は書き込みの**後**に行う。先に整理すると、新しいレコードが載った時点で上限＋1件に
  なってしまい、上限が言葉どおりの意味を持たなかった。メモリのみの経路(先に入れてから
  詰める)とも、同じ定数について食い違っていた。
- 復元は、対象タブのタブ以外の要素(通常ノード・サブフローの実体・junction・group)を、それぞれの
  種類に応じた API で全部消してから、スナップショットを入れ直す。
- スナップショットに junction と group が含まれていること(§7)が、復元で消えないための前提である。
- Restore 後はワークスペースを未保存状態にし、ユーザーがデプロイして確定できるようにする。

## 10. セキュリティ/境界の既定（前提）

- 全 HTTP エンドポイントは Node-RED の管理用ルート上にあり、データを扱うルートには
  `RED.auth.needsPermission` を明示的に付けている。Node-RED は自前で `adminAuth` を
  プラグイン登録ルートへ広げてはくれないためである。クライアントは `Common.apiFetch` 経由で
  エディタのベアラートークンを送る。静的アセットのルートは意図的に未認証のまま残している
  (タグ読み込みでヘッダを送れず、配るのはプラグイン自身の公開済みコードのみ)。
- API キーは暗号化して保存する(AES-256-GCM。旧 CTR 形式も読める)。ログ・エラー・
  クライアントログは出力前に秘匿情報を除去する。LLM へ送るフローコンテキストからも
  認証情報を取り除く。
- **Agent モードは受け入れたリスクの境界**: モデルの出力を確認なしで適用し、その中には
  `function` / `exec` ノードが含まれうる。すなわち設計上、任意コード実行である。
  ノード種別の許可リストは設けない(設けるとこのモードの意義が失われる)。詳細は
  architecture.md を参照。

## 11. 議論したい論点 / 既知のトレードオフ

このドキュメントを土台に議論したい主なポイント:

1. **group をどの型に分類するか**: 型判定は構造から推測する仕組みになっているため、group はエクスポート
   前は config ノード扱い、エクスポート後(座標が付いた状態)ではキャンバス要素扱いになる。現状は
   「レイアウトからだけ外す」ことで辻褄を合わせているが、group と junction を型判定そのものに明示的に
   書くべきかどうか。
2. **junction を LLM に見せるか**: 現状は見せていない(§7 の理由)。将来「LLM が junction 経由の配線を
   意識できた方がよい」場面があるか。見せる場合、エイリアスの割り当ての一貫性をどう保つか。
3. **暗黙のフロー指定で対象を取り違えるリスク**: 同じエイリアスが複数タブにある場合、推定は
   最初に見つかったタブを採用する。走査範囲をコンテキストフローに限定したことで実害は大きく
   減ったが、範囲内で曖昧なときの扱いをさらに厳密にすべきかどうか。
4. **あいまい一致をどこまで許すか**: ノードの照合は完全一致のみだが、地の文のノード名注釈やヒントの
   事前解決ではあいまい一致を使っている(一定の長さ以上かつ候補が1つに絞れるときだけ)。この線引きが
   妥当かどうか。
5. **エディタ認証への対応**: 認証を有効にした環境をサポート範囲に入れるかどうか。
6. **プロパティの中に残る生の ID**: ID をエイリアスへ置き換える処理は、プロパティの**トップレベルの
   文字列値**しか見ていない。配列や入れ子のオブジェクトの中に入った ID(たとえばリンクノードが持つ
   接続先 ID の配列)はそのままモデルに渡ってしまい、「LLM は ID を見ない」という §0 の建前から外れる。
   再帰的に置き換えるなら、戻す側のエイリアス→ID 復元も同じ深さまで対称にしなければならない
   (片方が取りこぼすと配線が壊れる)。

### 参考: エイリアス解決の優先順位
上から順に試し、最初に当たったものを採用する:

1. ID の完全一致
2. エイリアスの完全一致
3. 記号や大文字小文字のゆれを吸収した正規化後の一致
4. ノード名の一致
5. **完全一致のみを要求する呼び出しは、ここで打ち切る**
6. より緩い形でのエイリアス一致
7. 近似一致(一定の長さ以上あり、かつ候補が1つに絞れるときだけ)

「完全一致のみ」の指定は、ノードの照合(§4.3)や、ヒント・指示の事前解決で使う。弱い一致が
別のノードの ID を奪ってしまうのを防ぐためである。

## 12. 「作り直し」ではなく「差分適用」

### 作り直し方式の何が問題だったか
組み立て処理は、対象タブの**あるべき最終状態を丸ごと**作る。以前の適用はそれを最も単純な方法で
実現していた。タブの中のノード・junction・group を全部消してから、組み上がった一式を同じ ID のまま
入れ直す。結果は正しいが、そこに至る過程で**編集に無関係なノードまで一度破棄して作り直していた**。
エディタ自身の undo は筋が通らなくなり、スナップショットに漏れがあれば、それはそのまま削除に
なった（junction と group が消えていたのはこれである。§7）。

（なお、キャンバスの選択状態はどちらの方式でも解除される。再描画の共通処理が、描き直す前に
「選択をすべて解除」を実行するためである（消えたノードが選択に残ってはいけない）。差分適用が
狭めるのは「破棄される範囲」であって、「選択が解除される範囲」ではない。）

### 誤解しやすい点：デプロイでの再起動は起きていなかった
この方式でも、デプロイ済みのランタイムでノードが再起動されることはなかった。何を止めて何を
起動し直すかは Node-RED ランタイムの差分判定が決めており、その判定はノードを ID で突き合わせた
うえで **`x` / `y` / `wires` を意図的に無視する**（group ではさらに `nodes` / `style` / `w` / `h`）。
作り直しは ID を保持し、触っていないノードはスナップショットからそのまま持ち越すので、それらが
「変更あり」に分類されることはない。この性質は `test/deploy_churn.test.js` が同じ判定基準を実装して固定している。

（**Full deploy** は無条件に全再起動する。**Modified Flows** は配線が変わったノードや link で
つながったノードも止める。どちらもデプロイの種類の選択によるもので、適用方式の問題ではない。）

### 差分適用の分類
最終状態は同じまま、現在のキャンバスとの差分として当てる。

| 分類 | 処理 |
| --- | --- |
| 今あるが、もう不要 | 種類ごとの削除 API で消す |
| 必要だが、まだ無い | まとめて1回の import に渡す |
| 両方にあり、プロパティが違う | エディタ上のノードに直接書き込む |
| 両方にあり、座標だけ違う | 位置を代入して移動扱いにする |
| 両方にあり、配線が違う | リンク操作（下記） |
| 両方にあり、同一 | **一切触らない** |

### ワイヤは配列ではなくリンクである
エディタにおいて `node.wires` は正本ではない。接続は `{ source, sourcePort, target }` という独立した
オブジェクトとして別のレジストリに保持されており、エクスポート時にそこから `wires` が**導出**される。
つまり `node.wires` に代入しても何も変わらない。したがって配線の変更は、エディタ上のノードオブジェクトに
対してリンクの追加・削除 API を呼んで行う。削除 API は**オブジェクトの同一性**で照合するため、消す
リンクはエディタから取得したものでなければならない。組み立て直したリンクオブジェクトは何にも一致せず、
黙って無視される。追加ノードの import は配線処理より**前**に行う。新しいリンクは両端が存在しないと
張れないからである。

ここから2つの順序上の注意が出てくる。
- 追加ノード自身の `wires` は import の時点でリンクになる。一方、**再 import されなかったノードから
  そのノードへ向かうワイヤ**はならない。配線処理はそこを埋めるためにある。
- config ノードへの参照を張り替えるプロパティ更新では、書き込む**前に古い値に対して参照解除**を行い、
  書き込んだ後に登録し直す。そうしないと config ノード側の利用者リストに、もう使っていないノードが
  残り続ける。

### 差分適用を見送る条件
安全に表現できない変更に出会ったとき、差分適用は自分では処理せず、呼び出し側が従来の作り直し方式へ
フォールバックする。

- group が変更・追加・削除された
- ノードの group 所属が変わった
- group に属するノードが削除され、かつ **group 用の API が使えない**（後述）
- 既存の ID の type が変わった
- エクスポートを往復できないキャンバス要素がタブに存在する

**この判定が意味を持つには、マージで `g` が生き残っている必要がある。** `g` は
`MERGE_SKIP_KEYS` に入れてはいけない。他のどこでも埋め直されないため、入れると編集した
ノードが必ずグループ所属を失って返ってくるからである。それ自体が静かなデータ損失であり
（ノードはグループを抜けるのに、グループ側はそのノードを挙げ続ける）、同時に「group 所属が
変わった」判定が**通常のプロパティ編集のたびに**成立してしまう。つまりグループを使っている
フローでは差分適用が毎回見送られ、作り直しが走っていた。`g` を無条件に引き継いで安全なのは、
`g` が変換側の `META_KEY` だからである。スキーマからは読むことも書くこともできないので、
既存の値以外にありえない。

この関係のもう半分が group 自身の `nodes` 一覧で、こちらは Node-RED が自動では整合させない。
`RED.nodes.remove` にはグループの後始末が一切ない（エディタ標準の削除操作は先に
`RED.group.removeFromGroup` を呼んでいる）。両者を揃える処理が2箇所に要る。

- **マージ後の最終状態の側**: 削除の段階で、ワイヤを取り除くのと同じ要領で各 group の
  `nodes` からも削除済みの ID を落とす。適用処理に渡る時点で整合が取れている。
- **エディタのキャンバスの側**: ノードを削除する前に `RED.group.removeFromGroup` を呼ぶ。
  group はメンバーを**ノードの実体そのもの**として保持しているため、エクスポート形式の ID の
  配列を書き換えても反映されない。これが唯一の正しい手順である。先にノードを削除すると、
  group が存在しないノードを指し続けることになる。

group の `nodes` をプロパティ比較の対象から外している（`w` / `h` と同じ扱い）のはこのためである。
3つともメンバーから導かれる情報であり、所属の正本はノード側の `g` で、そちらは比較している。
一覧まで比較すると、所属の変更が2重に報告され、しかも2つ目の報告には安全な適用手段がない。

`removeFromGroup` はワークスペースがロックされていると何もせずに戻る。ここではその「黙って
何もしない」が最悪の結果になる。ノードだけが消え、group はそれを指したまま残るからである。
そこで差分適用は group 用の API が使える状態かを先に確認し、使えなければ見送る。作り直し方式は
この API を必要としない（group ごと入れ直すため）ので、同じ整合の取れた最終状態に、
より広い経路で到達する。

なお group まわりの変更は Vibe Schema からは到達できない（スキーマに group の概念がない）ので、
フォールバックは実用上のコストにならない。**正しさが「差分適用が全ケースを網羅していること」に
依存しない**という点が重要である。

### 失敗したときの戻し方
差分の途中で例外が出ると、キャンバスは中途半端に適用された状態になる。これは入れ直すだけでは
戻せない（追加された分が消えない）。そのためエラー経路では、タブを消してから「適用前」の
エクスポートを入れ直す。これは比較の土台に使ったものと同一のエクスポートなので、「適用前とは
何だったか」で両者が食い違うことはない。

**config ノードには専用の巻き戻しが要る。** config ノードは `z` を持たないためワークスペースの
エクスポートに最初から入っておらず、キャンバスを戻しても手が届かない。そのため以前は、失敗した
適用が「フローは無傷に見えるのに、接続先のブローカーだけ書き換わったまま」という状態を残していた。
そこで config ノードに触るときに、「これは元々存在しなかったので消し直す」か「上書きするキーの
元の値」かを記録しておく。値の記録は `hasOwnProperty` で判定するので、元々無かったキーは
`undefined` を書き戻すのではなく削除される。巻き戻しは新しいものから順に、かつキャンバスの復元の
**後**に行う。ワークスペースのノードを消すと、それらが config ノードの利用者リストから先に外れる
ためである。値と一緒に `changed` も戻す。このフラグはデプロイが読む対象なので、立てたままにすると
「当たらなかった編集」のために config ノードが再起動されてしまう。

- 回帰テスト: `test/incremental_apply.test.js`（何が触られたか）、
  `test/deploy_churn.test.js`（何が再起動されるか）、
  `test/import_safety.test.js` シナリオ B（キャンバスの巻き戻し）と
  シナリオ D（config ノードの巻き戻し）

## 13. 1つのキャンバスに対する2つの書き込み元の順序づけ

### 何が衝突するか
サイドバーの Import ボタンと Agent ノードは、どちらも同じキャンバスにフロー編集を適用する。
しかもノード側の応答が届くのはモデルの生成が終わった時点であり、誰かが選んだタイミングではない。
この2つを隔てるものが何もなかった。

**壊れるのは2番目の編集ではなく、1番目の編集である。** 適用は「現在のフローに対するマージ」
（§0・§3）なので、2番目の適用がスナップショットを取る時点で、1番目の編集はすでにそこにある。
デプロイもレビューもされていない状態のまま、2番目の編集がマージする土台に組み込まれてしまう。
結果として両方の変更がキャンバスに載り、2番目の適用が保存したチェックポイントは「1番目の編集を
すでに含む状態」を指すため、どちらもきれいに取り消せなくなる。

### 規則
**適用済みかつ未デプロイのフローは保留（held）扱いとし、** そのフローを対象とする他の要求は待機する。
対象フローが重ならない適用同士は待たない。待機する場合は、先に届いた要求から順に処理する。

「デプロイまで保留」という境界が妥当なのは、それがランタイム側の境界と一致しているからである。
デプロイまでの間、その編集はエディタの中にしか存在しない。レビューするのも、取り消すのも、
復元するのも利用者の判断であり、そこへ2番目の編集がマージすると、その判断の機会を奪ってしまう。
デプロイ後はそれが単に「現在のフロー」であり、次の編集がそこへマージするのは本来の動作である。

### キューを置く場所
**サーバ側**（`apply_queue_server.js`）に置く。適用処理そのものは移せない。管理 API 経由で
フローを書き戻してもエディタの未保存状態を消せないためで、これがブラウザ内で適用している理由
そのものである。しかし**順序づけ**をブラウザに置く理由はなく、置くと次の3つが成り立たなくなる。

- **エディタが2つあればキューも2つになる。** 1つのブラウザの中でサイドバーと Agent ノードを
  順序づけても、同じフローを編集している2人の間では何も調停されない。しかも Agent ノードの
  応答は接続中の**すべての**エディタへ配信されるので、それぞれが自分の見ているフローに対して
  適用してしまう。
- **ブラウザは自分のデプロイしか見えない。** 解除の signal はデプロイでなければならないが、
  エディタの `deploy` イベントは、そのデプロイを行ったブラウザでしか発火しない。
- **タブを閉じられるとキューが止まる。** 取った順番が戻ってこないことを、ブラウザの外からは
  誰も検知できない。

クライアントは順番を要求し、付与されるのを待ち、適用し、結果を報告する。状態は comms
（`llm-plugin/apply-queue`、retain 付き）で全エディタへ配信する。retain させているので、
途中から開いたエディタにも「いま何が待っているか」がすぐ表示される。

### 保留の解除
デプロイが完了すると、ランタイムが `runtime-event`（id は `runtime-deploy`）を発行する。
キューはこれを購読する。フローエンジンが使っているものと同一のイベント発行元
（`@node-red/util` の `events`。プラグインには `RED.events` として公開されている）なので、
**どのエディタからの Deploy でも**、Agent ノードの自動デプロイ（`core:deploy-flows` を通るので
Deploy ボタンと同じ経路）でも、さらにはエディタですらないものが管理 API 経由で行ったデプロイでも
発火する。後ろの2つはブラウザからは見えない。

したがって、自動デプロイを有効にした無人のノードは自分で保留を解除し、自動デプロイなしの
ノードは利用者のデプロイを待ち、誰か1人の Deploy が全員に対してそのフローを解放する。
これらがすべて1つの購読でまかなえ、場合分けは不要である。

デプロイイベントでは解除されない場合が2つあり、どちらも行き詰まらないようサイドバーのキュー
パネルに操作を出している。

- **失敗した適用は何も保留しない。** 取り込み処理がロールバックするので、キャンバスには何も
  確定していない。ここで保留すると、起こる理由のないデプロイを次の要求が待ち続けることになる。
- **手作業での取り消しや、チェックポイントの復元**は、デプロイを経ずに編集を終わらせる。
  この場合は **Release** で保留を手動解除する。待機中の要求は取り消すこともでき、
  取り消したことは呼び出し元へ通知される（応答が返らないまま放置されることはない）。
- **順番を取ったブラウザが閉じられた場合**、そのままでは全員が待たされる。付与された順番が
  `GRANT_TIMEOUT_MS` 以内に完了報告されなければ失効させ、`HOLD_MAX_AGE_MS` を超えた保留も
  最終手段として解除する。失効の判断が誤っていた場合の代償は「適用が1回重複して試行される」
  ことだが、時間切れを設けない場合の代償は「キューが二度と動かなくなる」ことである。

**対象範囲が宣言されていない適用**（フローコンテキストを1つも選んでいない場合）は、
読み書きのどちらもどのフローに及ぶか分からないため、双方向にすべてと衝突する扱いとする。
ここで推測を入れることが、誰も見ていない場所へ編集が着地する原因になる。

### 何を守り、何を守らないか
1つの Node-RED につながっているすべてのエディタが対象になる。「複数人で同じフローを触る」は
実務上これを意味する。一方、そのランタイムの外までは及ばない。ストアを共有する2つの Node-RED
インスタンスは、それぞれ別のキューを持つ。

書き込みの瞬間については、引き続き Node-RED 自身の保護が最後の砦になる。フローの POST には
リビジョンが含まれ、古いリビジョンに対するデプロイは `409` で返って、エディタ標準のマージ競合
ダイアログが開く。このキューが扱うのはその**手前の区間**、すなわち編集が適用済みかつ未デプロイの
まま置かれている時間であり、そこはリビジョン照合では見えない。

- 回帰テスト: `test/apply_queue.test.js` がサーバ側の規則を検証する（対象が異なれば待たない、
  同じ対象ではデプロイまで待つ、到着順が保たれる、他のエディタからのデプロイでも保留が解除される、
  失敗時は何も保留しない、範囲不明の適用はすべてを保留する、放棄された順番は失効する、
  変更が必ず配信される）。`test/apply_queue_client.test.js` がブラウザ側の手順を検証する
  （順番が付与されるまで適用しない、同じ付与が再配信されても二重に適用しない、失敗時も報告して
  順番を手放す、他のエディタへの付与を自分で実行しない）。
