# 設計ノート — 処理フロー・ルール・優先順位とその理由

このドキュメントは、LLM プラグインが「ユーザーの指示 → LLM の応答 → フローへの反映」をどういう
**順序・ルール・優先順位**で行うか、そして **なぜそう実装されているか(理由)** をまとめたものです。
実装を議論するための共通の土台として使うことを目的としています。

- モジュール別の「何をするか」のリファレンス → [architecture.md](./architecture.md)
- 中間表現(Vibe Schema)の仕様 → [vibe-schema.md](./vibe-schema.md)
- レイアウトエンジンの詳細 → [layout.md](./layout.md)

このノートはそれらと重複せず、**設計判断と優先順位の「なぜ」** に集中します。

---

## 0. 設計の柱(なぜこの形か)

| 判断 | 理由 |
|------|------|
| **決定論的な処理はコード、意味づけだけ LLM** | この切り分けが他のすべての柱の前提になっている。**一意に決まるもの**(ノード ID の発番と衝突回避、座標、接続配列の組み立て、エイリアスの採番、junction / group の保全)は必ずコード側が担当する。**LLM に委ねるのは「ノード同士の論理的なつながり」と「ノード内の設定」だけ**。確率的な出力に決定論的な仕事をさせると、ID の重複・座標の破綻・ワイヤの取り違えという形で必ず失敗が表面化し、しかもその失敗は検証しづらい。逆に「この inject を 5 分周期にして debug につなぐ」といった意味づけは、コードでは決められない。 |
| **中間表現「Vibe Schema」を挟む** | 上の切り分けを構造として強制するための境界。Node-RED の生の JSON はランダムな ID・座標・型ごとの内部配列を含み、LLM が安定して生成・編集できるものではない。「種類と名前から作った人間に読めるエイリアス」を鍵にし、座標を持たない表現へ抽象化することで、LLM は ID を発明できず、座標を気にする必要もなくなる。 |
| **アンダースコア始まりのプロパティ＝メタデータ、LLM には渡さない** | エイリアス・宣言順・コメントの貼り付け先といった「コード側から次の工程への申し送り」は、アンダースコアで始まるキーとしてノードに載せる。この命名規約ひとつに、境界の両方向を紐づけている(§0.1)。 |
| **適用は必ず「マージ」** | LLM は毎回フロー全体を返すわけではなく、部分編集の方が普通である。「列挙されたものだけ追加・更新、空を指定されたものは削除、言及がないものは現状維持」に固定しておけば、応答が不完全でも既存フローは壊れない。適用方法をモデルに選ばせる分岐は持たない。誤爆したときに既存フローが壊れる側へ倒れるためである。 |
| **反映はエディタ側(ブラウザ)で行う** | サーバから管理 API 経由で書き戻すと、開いているエディタの未保存状態(編集中の印やハイライト)を消せず、ユーザーの手元と食い違う。だからブラウザ内から直接キャンバスへ反映する。サイドバーからでも Agent ノードからでも同じである。 |
| **破壊的変更の前に必ずチェックポイント** | 適用はワンクリックで元のフローを書き換えてしまう。だから適用の直前に対象フローを丸ごと控え、メッセージ単位で「元に戻す」を可能にしておく。エディタ標準の操作履歴には積まず、プラグイン独自の控えで巻き戻す。 |
| **控えは「完全なフロー」でなければならない** | 適用は「対象ワークスペースをいったん消して作り直す」方式なので、控えに入っていないキャンバス要素はそのまま消える。したがって junction と group も含める必要がある(§7)。 |

### 0.1 メタデータ境界(アンダースコア始まりのプロパティ)

判定は一箇所にまとめてある —「キー名がアンダースコアで始まるか」だけ。この1つの規約で
**往路と復路の両方**を縛る。

| 方向 | 規則 | 実装箇所 |
|------|------|----------|
| **往路(LLM へ)** | 中間表現へ変換する側は、アンダースコア始まりのキーを一切出力しない。ID・所属タブ・座標・接続配列・所属グループも同様に落とす。結果としてモデルが受け取るのは **エイリアス・種類・名前・型ごとのプロパティ・接続だけ**になる。 | `flow_converter_core.js` `toIntermediate` |
| **復路(LLM から)** | Node-RED の形へ戻す側は、スキーマに書かれたアンダースコア始まりのキーを**無視する**(トップレベルでもプロパティの中でも)。メタデータを書けるのはこのモジュール自身だけで、モデルには偽装できない。自動生成した config の仮置きノードの印も、スキーマ上のフラグではなく変換中のローカルな記録として持つ。 | `flow_converter_core.js` `toNodeRed` |
| **キャンバスへ** | インポート側は2回に分けてメタデータを剥がす。1回目はマージ完了直後で、このときレイアウトがまだ必要とする並び順と貼り付け先の情報だけを残す。2回目はレイアウト後で、残りも落とす。**キャンバスへ渡る時点でアンダースコア始まりのキーはゼロになる。** | `importer.js` `rebuildWorkspaceFromSnapshot` |

- **理由**: 個別のキー名を名指しで消して回る方式だと、メタデータを1つ増やすたびに削除漏れが
  起きる(実際、コメントの貼り付け先を示す印がレイアウトに使われたあと、そのままキャンバスへ
  流れていたことがある)。命名規約でまとめて弾く形にすれば、新しいメタデータを足しても境界は
  自動的に守られる。
- **モデルが偽装できないことも規約の一部である**: たとえば「LLM がどのキーに言及したか」の記録
  (§4.2 のプロパティ保存の判断に使う)や「自動生成した仮置きノードである」という印(§5 の
  config 保護に効く)をスキーマから書けてしまうと、マージ規則そのものを LLM の出力で
  曲げられてしまう。
- 回帰テスト: `test/metadata_props.test.js`(`npm test` に登録)。

## 1. データフロー(全体像)

```
ユーザー入力
   │  (モード = Ask / Agent、対象フローの選択)
   ▼
サイドバー ──送信──► HTTP 層 ─► 共有 LLM エンジン ─► Ollama / OpenAI / Custom
   │                                    │
   │   ┌── LLM へ渡すコンテキスト: 選択したフローを取り出し、中間表現へ変換
   │   │   （junction / group は含めない ＝ モデルが見るエイリアス採番を変えない）
   ▼   ▼
応答テキスト（説明 + 必要なら Vibe Schema のコードブロック）
   │
   ├─ Ask  : ユーザーが「Import」ボタンを押したら適用
   └─ Agent: 応答を受け取った時点で自動的に適用
   │
   ▼
応答からフローへ反映する処理   ← 適用の中枢
   │
   ├─ 0) 適用直前のフローを控える（ボタンが押された時点で実行）
   ├─ 1) 対象タブの決定 — 書き込み範囲の限定と、暗黙のフロー指定の補完（§6）
   ├─ 2) 応答の解析 — ノード・接続のヒント・削除や再配置の指示を取り出す
   ├─ 3) 対象タブの現状を取得（junction / group を含めた完全な形で）
   ├─ 4) 削除 → 追加/更新 → 接続 の3段階で組み立て直す（§3）
   └─ 5) 対象タブをいったん消して、組み立てた結果を入れ直す（§7）
```

Agent モードのランタイムノードも、応答をエディタへ送り、エディタ側で受け取った側が同じ適用処理を
呼ぶ。**適用ロジックはサイドバーと完全に共通である。**

## 2. Ask / Agent の違いと理由

| | Ask | Agent |
|--|-----|-------|
| 適用契機 | ユーザーが Import を押す | 応答受信後に自動 |
| 用途 | 内容を確認してから反映したい | 反復・自動化 |
| 共通点 | 適用ロジック・チェックポイント・マージ規則はすべて同じ | 同左 |

- **モードの違いは「いつ適用するか」だけ**にしてある。適用の中身を分岐させると片方だけ壊れるバグの
  温床になるため、適用処理はモードをほとんど見ない。唯一の例外は応答の解釈で、Agent のときだけ
  部分スキーマを現在のフローに重ねてから読む。

---

## 3. 適用の3段階（削除 → 追加/更新 → 接続）と、その順序の理由

再構築は必ず次の順で処理する。**順序そのものがルール**であり、1つのスキーマが自己矛盾していても
破綻しないための設計である。

### 第1段階: 削除
- 削除指示(エイリアスに空を指定したもの)で名指しされたノードを、控えておいたフローから除く。
- 除いた ID を覚えておき、**第2段階が同じエイリアスを再び持ち込むのを禁じる**。
- **理由**: 「いったん消して作り直す」系の応答では、削除対象と同じ名前の新規ノードが同じスキーマに
  同居することがある。そのとき削除の意図を優先できる。

### 第2段階: 追加・更新
- 残ったフローをノード ID 引きにして、提案されたノードをマージする。
- **Config Node 保護**: 既存にない config ノードは追加しない(§5)。
- **ワイヤは足し算でマージする**: 既存ノードと一致した場合、既存の接続先と提案された接続先を
  出力ポート単位で足し合わせる。**接続を切るのは明示的な切断指示だけ**(§4)。
- **プロパティ保存**: LLM が触れていないキーは既存の値に戻す(§4)。

### 第3段階: 接続
- **1つに統合した索引**を作る(ここが肝心である):
  - 既存ノードの自動エイリアス、新規ノードが名乗るエイリアス、ノード名、ID を、すべて同じ索引から引く。
  - これがないと「既存の inject から新規の function へ」という接続で、送信元は解決できても送信先が
    解決できない。新規ノードは自動採番だと単に種類名になり、LLM が付けた名前と一致しないためである。
- 存在しない ID 宛のワイヤを掃除し、切断指示を適用してから、スキーマの接続を張る。
- **なぜ接続を最後にするか**: 接続の両端は「削除も追加も済んだ最終的なノード集合」に対して解決しな
  ければならない。削除・追加より先に接続を確定すると、すでに消えたノードやまだ無いノードを指してしまう。

## 4. マージのルール（既存を壊さないための優先順位）

### 4.1 ワイヤ: 既定は「足す」、切るのは明示されたときだけ
- 既存の接続先と提案された接続先を、出力ポート単位で足し合わせ、重複は取り除く。
- 切断するのは、LLM が接続の削除を明示的に書いたときだけである。
- **理由**: LLM は編集対象ノードの接続を書き落としがちである。省略を「切断の意図」と解釈すると、
  無関係な既存接続まで勝手に消える。「接続が勝手に切られる」という不満を生まないための既定。

### 4.2 プロパティ: 「言及していないキーは既存のまま」
- LLM が明示的に設定したキーの集合をどう得るか:
  - Vibe Schema 経路では、変換の時点で「スキーマに実際に書かれていたキー」を記録しておく。
  - 生の JSON 経路では、値が入っているキーをそう見なす。
- それ以外のキーは、既存ノードの値に戻す。
- ただし同一性(ID・種類)、配置(所属タブ・座標・所属グループ)、接続、エディタの編集状態、および
  メタデータは引き継がない。これらは「プロパティ」ではなく、別のルールが決めるものだからである。
- **理由**: 変換時に型ごとの既定値(たとえば debug ノードの出力対象の指定)が補われても、ユーザーが
  以前に設定した値を上書きしない。「触っていない設定は保持される」を保証するためである。

### 4.3 ノードの照合: 完全一致のみ、あいまい一致は使わない
- 提案されたノードを既存ノードに割り当てるときは、**エイリアスの完全一致だけ**で判定する。
- **理由**: LLM にはプロンプトで既存エイリアスをすべて渡してある。一致しないエイリアスは「新規に
  作りたい」という意図だと解釈できる。ここであいまい一致を許すと、新しく作りたい `inject_py_1` が
  既存の `inject` に前方一致してしまい、無関係なノードを黙って上書きする。**「取り違えて上書き」
  より「新規として追加」の方が安全である。**

## 5. Config Node 保護

- LLM は config ノード(ブローカー設定や実行環境設定など)を **作成も削除もできない**。既存のものを
  エイリアスで参照するだけである。これはプロンプトと適用側の両方で強制している。
- 同種の config ノードが1つしかない場合は、その既存のものを再利用する。同じ設定が二重にできるのを
  防ぐためである。
- **理由**: config ノードは認証情報や接続先といった「壊れると影響範囲が広い」共有資源である。LLM が
  勝手に作ったり消したりして他のフローを巻き込む事故を防ぐ。config ノードはすべてコンテキストに
  含めたうえで、「参照は自由、生成と削除は不可」という非対称なルールにしている。

## 6. マルチフロー / 暗黙のフロー指定

- スキーマのノードにどのタブのものかが書かれていれば、タブごとに分割して適用する。
- **暗黙の指定**: LLM がその指定を書き忘れても、スキーマ上のエイリアスや接続が複数タブの既存ノードと
  対応づけられる場合、「このエイリアスはどのタブのものか」を割り出し、接続をたどって新規ノードにも
  隣のノードの所属を継承させる。
- **理由**: 「MCU 側 / Server 側」のように複数タブにまたがる指示では、LLM はタブの指定を落としがちで
  ある。指定がないと接続がアクティブタブの境界を越えられず、「送信側のノードに何もつながらない」と
  いう症状になる。そこを推定で補う。

### 走査範囲はコンテキストフローに限定する（必須）

推定も、タブ名の解決も、複数フローへの振り分けも、**LLM にコンテキストとして渡したフロー**の中だけを
走査する。全ワークスペースを走査してはならない。

- **理由**: 自動生成されるエイリアスが一意なのは**フローの中だけ**であり、タブをまたげば普通に衝突する。
  「エイリアスはどのタブのものか」の対応づけは先に見つかった方が勝つので、全部を走査すると
  「タブバーで手前にあるだけの無関係なフロー」が同名のエイリアスを先取りし、編集がまるごとそちらへ飛ぶ。
  しかも適用は対象キャンバスを**消してから**作り直すため、誤爆は追加では済まず破壊的になる。さらに
  チェックポイントはコンテキストフローの範囲でしか控えていないので、Restore でも戻せない。
- 範囲を絞ることで「書き込む範囲 ⊆ 控えてある範囲」が常に成り立ち、Restore がいつでも有効になる。
- アクティブタブが範囲外のとき(送信後にユーザーがタブを切り替えた場合など)は、アクティブタブではなく
  コンテキストフローを対象にする。範囲指定がない(フローを1つも選んでいない)ときだけ、従来どおり
  アクティブタブを対象とする。
- 実際に置き換える直前の最終確認で、対象が範囲外なら**中止**する。
- リグレッションテスト: `test/cross_flow_isolation.test.js`(エイリアス衝突 / タブ切替 / 複数フローへの
  波及 / 範囲外のタブ指定 / 範囲指定なしのときの後方互換)。

## 7. スナップショットの完全性と junction / group

### 前提（Node-RED エディタの内部構造）
- タブを指定してノードを取り出すエディタの標準 API は、**通常ノードしか返さない**。junction と group は
  それぞれ別のレジストリで管理されており、専用の取得 API を呼ばないと手に入らない
  (Node-RED 4.1.7 のエディタクライアントで確認)。
- 適用も復元も、対象タブの junction と group を**全部消してから**フローを入れ直す。したがって、控えに
  入っていない要素はそのまま消える。さらに接続の段階で「作り直したフローに存在しない ID 宛」の
  ワイヤは掃除されるため、junction が控えから欠けると、そこへ向かうワイヤまで行き先なしとして切られる。

### 設計（必要な場所だけが取り込む）
- フローを取り出す関数に「junction と group も含める」オプションを設け、有効にしたときだけ控えに含める。
  エディタ標準のエクスポートは、junction を接続情報つきで正しく書き出してくれる。
- **フローを作り直す2箇所だけがこのオプションを使う**:
  - 適用時の再構築の土台を取るところ
  - チェックポイントを控えるところ
- **LLM に渡すコンテキストと、応答中のノード名注釈は、このオプションを使わない**。
  - **理由**: この2つは中間表現へ変換するときのエイリアス採番を共有している。junction と group を
    混ぜると、モデルが見るエイリアスの並びが変わり、生成の挙動そのものが変わってしまう。
    **適用側だけが完全なフローを使い、生成側は従来どおり**にすることで、この不具合の修正が
    生成品質に影響しないよう切り分けた。

### レイアウトから group を外す理由
- junction は座標と接続を持つので、キャンバス上の実体として扱われる。実際に配線が通る点なので、
  レイアウトの隣接関係に含めてよい(位置は既存ノードの座標として保持される)。
- group も座標を持つため同じくキャンバス上の実体として扱われるが、**group の外形は自分のメンバーを
  囲むように決まる**。これを重なり解消の処理に渡すと「自分の中身と重なっている」と判定され、破綻する。
- そこで「キャンバス上の実体であり、かつ group ではないもの」という判定を別に設け、レイアウトの
  呼び出しにはこちらを使う。**group はレイアウトの対象から外し、位置は元のまま保つ。**
- 回帰テスト: `test/junction_preserve.test.js`(`npm test` に登録)。junction を挟んだ流れを編集し、
  junction 自体と前後両方向のワイヤが残ることを検証する。

## 8. レイアウトの優先順位（詳細は layout.md）

- **既存フローがある場合は差分配置**: 既存ノードの座標は編集前の位置に戻し、新規ノードだけを
  隣接ノードの右または左に置く。長い鎖の折り返しは無効にする(既存の形を保つため)。
- **完全な新規のときだけ全体再配置**: このときは長い鎖を折り返して収める。
- **間隔は「ノードの縁と縁のあいだの余白」**であり、中心間の距離ではない。ノード幅は、可能なら
  エディタが実測した値を使い、名前が変わって実測値が当てにならないときは推定値に切り替える。
- 再配置指示は名指しされた一群だけを並べ直し、元の左上位置に戻すので他は動かない。削除して作り直すと
  ID が変わってしまうため、ID を保ったまま整列し直せることに意味がある。

## 9. チェックポイント(巻き戻し)の考え方

- 適用の**直前**に対象フローを控え、それを該当メッセージに紐付ける。メッセージ横の Restore ボタンが
  そこまで巻き戻す。
- 復元は、対象タブのタブ以外の要素(通常ノード・サブフローの実体・junction・group)を、それぞれの
  種類に応じた API で全部消してから、控えを入れ直す。
- 控えに junction と group が含まれていること(§7)が、復元で消えないための前提である。
- Restore 後はワークスペースを未保存状態にし、ユーザーがデプロイして確定できるようにする。

## 10. セキュリティ/境界の既定（前提）

- 全 HTTP エンドポイントは Node-RED の管理用ルート上にある。**エディタ認証はオフである前提**で
  作っている。オンにした場合に未認証で到達しうる点は既知の未対応であり、対応するにはクライアント側から
  認証トークンを付けて呼ぶ必要がある。
- API キーは暗号化して保存する。ログ・エラー・クライアントログは出力前に秘匿情報を除去する。LLM へ送る
  フローコンテキストからも認証情報を取り除く。

## 11. 議論したい論点 / 既知のトレードオフ

このドキュメントを土台に議論したい主なポイント:

1. **group をどの型に分類するか**: 型判定は構造から推測する仕組みになっているため、group はエクスポート
   前は config ノード扱い、エクスポート後(座標が付いた状態)ではキャンバス要素扱いになる。現状は
   「レイアウトからだけ外す」ことで辻褄を合わせているが、group と junction を型判定そのものに明示的に
   書くべきかどうか。
2. **junction を LLM に見せるか**: 現状は見せていない(§7 の理由)。将来「LLM が junction 経由の配線を
   意識できた方がよい」場面があるか。見せる場合、エイリアス採番の一貫性をどう保つか。
3. **暗黙のフロー指定の誤爆リスク**: 同じエイリアスが複数タブにある場合、推定は最初に見つかったタブを
   採用する。走査範囲をコンテキストフローに限定したことで実害は大きく減ったが、範囲内で曖昧なときの
   扱いをさらに厳密にすべきかどうか。
4. **あいまい一致をどこまで許すか**: ノードの照合は完全一致のみだが、地の文のノード名注釈やヒントの
   事前解決ではあいまい一致を使っている(一定の長さ以上かつ候補が1つに絞れるときだけ)。この線引きが
   妥当かどうか。
5. **エディタ認証への対応**: 認証を有効にした環境をサポート範囲に入れるかどうか。
6. **プロパティの中に残る生の ID**: ID をエイリアスへ置き換える処理は、プロパティの**トップレベルの
   文字列値**しか見ていない。配列や入れ子のオブジェクトの中に入った ID(たとえばリンクノードが持つ
   接続先 ID の配列)はそのままモデルに渡ってしまい、「LLM は ID を見ない」という §0 の建前から外れる。
   再帰的に置き換えるなら、戻す側のエイリアス→ID 復元も同じ深さまで対称にしなければならない
   (片方が取りこぼすと配線が壊れる)。

### 参考: エイリアス解決の優先順位
上から順に試し、最初に当たったものを採用する:

1. ID の完全一致
2. エイリアスの完全一致
3. 記号や大文字小文字のゆれを吸収した正規化後の一致
4. ノード名の一致
5. **完全一致のみを要求する呼び出しは、ここで打ち切る**
6. より緩い形でのエイリアス一致
7. 近似一致(一定の長さ以上あり、かつ候補が1つに絞れるときだけ)

「完全一致のみ」の指定は、ノードの照合(§4.3)や、ヒント・指示の事前解決で使う。弱い一致が
別のノードの ID を奪ってしまうのを防ぐためである。
