# 設計ノート — 処理フロー・ルール・優先順位とその理由

このドキュメントは、LLM プラグインが「ユーザーの指示 → LLM の応答 → フローへの反映」をどういう
**順序・ルール・優先順位**で行うか、そして **なぜそう実装されているか(理由)** をまとめたものです。
実装を議論するための共通の土台として使うことを目的としています。

- モジュール別の「何をするか」のリファレンス → [docs/jp/architecture.md](./architecture.md)
- 中間表現(Vibe Schema)の仕様 → [docs/jp/vibe-schema.md](./vibe-schema.md)
- レイアウトエンジンの詳細 → [docs/jp/layout.md](./layout.md)

このノートはそれらと重複せず、**設計判断と優先順位の「なぜ」** に集中します。

## 0. 設計の柱(なぜこの形か)

| 判断 | 理由 |
|------|------|
| **決定論的な処理はコード、論理的な思考は LLM** | この切り分けが他のすべての柱の前提になっている。**一意に決まるもの**(ノード ID の生成と重複回避、座標、接続配列の組み立て、エイリアスの割り当て、junction / group の保全)は必ずコード側が担当する。**LLM に委ねるのは「ノード同士の論理的なつながり」と「ノード内の設定」だけ**。確率的な出力に決定論的な仕事をさせると、ID の重複・座標の破綻・ワイヤの取り違えという形で必ず失敗が表面化し、しかもその失敗は検証しづらい。逆に「この inject を 5 分周期にして debug につなぐ」といった文脈からの意味づけは、コードでは決められない。 |
| **中間表現「Vibe Schema」を挟む** | 上の切り分けを構造として強制するための境界。素の Node-RED JSON はランダムな ID・座標・型ごとの内部配列を含み、LLM が安定して生成・編集できるものではない。「種類と名前から作った人間に読めるエイリアス」を鍵にし、座標を持たない表現へ抽象化することで、LLM は ID を発明できず、座標を気にする必要もなくなる。 |
| **アンダースコア始まりのプロパティ＝メタデータ、LLM には渡さない** | エイリアス・宣言順・コメントの貼り付け先といった「コード側から次の工程への申し送り」は、アンダースコアで始まるキーとしてノードに載せる。この命名規約ひとつに、境界の両方向を紐づけている(§0 メタデータ境界)。 |
| **適用は必ず「マージ」** | LLM は毎回フロー全体を返すわけではなく、部分編集の方が普通である。「列挙されたものだけ追加・更新、`delete` に挙げたものは削除、言及がないものは現状維持」に固定しておけば、応答が不完全でも既存フローは壊れない。適用方法をモデルに選ばせる分岐は持たない。判断を誤ったときに、既存フローが壊れる側へ倒れるためである。 |
| **反映はエディタ側(ブラウザ)で行う** | サーバから管理 API 経由で書き戻すと、開いているエディタの未保存状態(編集中の印やハイライト)を消せず、ユーザーの手元と食い違う。だからブラウザ内から直接キャンバスへ反映する。 |
| **破壊的変更の前に必ずチェックポイント** | 適用はワンクリックで元のフローを書き換えてしまう。だから適用の直前に、対象フローを丸ごとスナップショットとして保存し、メッセージ単位で「元に戻す」を可能にしておく。エディタ標準の操作履歴には積まず、プラグイン独自のスナップショットで巻き戻す。 |
| **スナップショットは「完全なフロー」でなければならない** | スナップショットは、マージの土台であると同時に、失敗したときに戻す先でもある。さらにフォールバック時の適用は今でも対象タブを消すので、スナップショットに入っていないキャンバス要素は消えてしまう。したがって junction と group も含める必要がある(§7)。 |
| **応答が触れていないものは残す** | 複数の仕組みの背後にある1つの規則である。応答が触れていないものはそのまま残し、取り除くには明示的な指示が要る。ワイヤは追加され、書かれていないことを理由に切られない(§4.1)。触れていないプロパティは値を保つ(§4.2)。Config ノードは作りも消しもしない(§5)。junction とグループはスナップショットに含める(§7)。グループの枠はユーザーのもので、応答は枠を作れず、編集も削除もできない。空になったことを理由にも消えない(§15)。**位置だけは例外**で、レイアウトは誰が置いたかに関係なくキャンバス全体を整理する。すべての枠を合わせて揃え、すべての重なりを解消する。保つのはフローの形だけで、触れていないフローは平行移動するだけで組み直さない([layout.md](./layout.md))。新しい仕組みもこの既定から始める。 |
| **プラグインは通知を出さない** | 通知としてユーザーに届くのは Node-RED 自身のシステム通知(デプロイ結果など)だけである。プラグインはうまくいったときには何も言わず、伝えるべき警告やエラーはチャット欄の1行として出す(`Common.notice`)。この行はチャット履歴には残らない。 |

### メタデータ境界(アンダースコア始まりのプロパティ)

判定は一箇所にまとめてある —「キー名がアンダースコアで始まるか」だけ。この1つの規約で
**往路と復路の両方**を縛る。

| 方向 | 規則 | 実装箇所 |
|------|------|----------|
| **往路(LLM へ)** | 中間表現へ変換する側は、アンダースコア始まりのキーを一切出力しない。ID・所属タブ・座標・接続配列・所属グループも同様に落とす。結果としてモデルが受け取るのは **エイリアス・種類・名前・型ごとのプロパティ・接続だけ**になる。 | `flow_converter_core.js` `toIntermediate` |
| **復路(LLM から)** | Node-RED の形へ戻す側は、スキーマに書かれたアンダースコア始まりのキーを**無視する**(トップレベルでもプロパティの中でも)。メタデータを書けるのはこのモジュール自身だけで、モデルには偽装できない。自動生成した config の仮置きノードの印も、スキーマ上のフラグではなく変換中のローカルな記録として持つ。 | `flow_converter_core.js` `toNodeRed` |
| **キャンバスへ** | インポート側は2回に分けてメタデータを剥がす。1回目はマージ完了直後で、このときレイアウトがまだ必要とする並び順と貼り付け先の情報だけを残す。2回目はレイアウト後で、残りも落とす。**キャンバスへ渡る時点でアンダースコア始まりのキーはゼロになる。** | `importer.js` `rebuildWorkspaceFromSnapshot` |

- **理由**: 個別のキー名を名指しで消して回る方式だと、メタデータを1つ増やすたびに削除漏れが
  起きる(実際、コメントの貼り付け先を示す印がレイアウトに使われたあと、そのままキャンバスへ
  流れていたことがある)。命名規約でまとめて除外する形にすれば、新しいメタデータを足しても境界は
  自動的に守られる。
- **モデルが偽装できないことも規約の一部である**: たとえば「LLM がどのキーに言及したか」の記録
  (§4.2 のプロパティ保存の判断に使う)や「自動生成した仮置きノードである」という印(§5 の
  config 保護に効く)をスキーマから書けてしまうと、マージ規則そのものを LLM の出力で
  曲げられてしまう。
- 回帰テスト: `test/unit/schema_conventions.test.js`(`npm test` に登録)。

## 1. データフロー(全体像)

```
ユーザー入力
   │  (モード = Ask / Agent、対象フローの選択)
   ▼
サイドバー ──送信──► HTTP 層 ─► 共有 LLM エンジン ─► Ollama / OpenAI / Custom
   │                                    │
   │   ┌── LLM へ渡すコンテキスト: 選択したフローを取り出し、中間表現へ変換
   │   │   （junction を通るワイヤはその先への接続として見せる。group は落とす。
   │   │   どちらがあってもモデルが見るエイリアスの割り当ては変わらない — §7, §15）
   ▼   ▼
応答テキスト（説明 + 必要なら Vibe Schema のコードブロック）
   │
   ├─ Ask  : ユーザーが「Import」ボタンを押したら適用
   └─ Agent: 応答を受け取った時点で自動的に適用
   │
   ▼
応答からフローへ反映する処理   ← 適用の中枢
   │
   ├─ 0) 適用直前のフローをスナップショットに保存（ボタンが押された時点で実行）
   ├─ 1) 対象タブの決定 — 書き込み範囲の限定と、暗黙のフロー指定の補完（§6）
   ├─ 2) 応答の解析 — ノード・接続のヒント・削除や再配置の指示を取り出す
   ├─ 3) 対象タブの現状を取得（junction / group を含めた完全な形で）
   ├─ 4) 削除 → 追加/更新 → 接続 の3段階で組み立て直す（§3）
   └─ 5) 組み立てた結果を「差分」として当てる（§12）
        └─ 差分で表現できない変更のときだけ、従来どおり対象タブを消して
           入れ直す方式にフォールバックする（§12）
```

## 2. Ask / Agent の違いと理由

| | Ask | Agent |
|--|-----|-------|
| 問いの種類 | 「このフローは何をしている? どこが悪い?」 | 「このフローをこう変えて」 |
| システムプロンプト | `prompt_ask.txt` — フローを読んで説明する。提案は**しない** | `prompt_system.txt` — Vibe Schema の規約 |
| 応答 | 文章。どのノードが悪く、どのプロパティを直すか。ノードはエイリアスをバッククォートで囲む | スキーマ。キャンバスへ適用される |
| 共通点 | フローコンテキスト、エンジン、プロバイダ。そして応答がスキーマを含む場合の適用規則 | 同左 |

- **この2つは「同じ問いを後で違う扱いにする」のではなく、別の問いである。** 以前は
  まったく同じリクエストを送り、返ってきたものをサイドバーがどう扱うかだけが違っていた。
  その結果、Ask で「debug ノードを足して」と聞くとフローが返ってきて、ユーザーが手で
  Import する羽目になっていた。モードは「読むだけ」と言っているのに、モデルは提案して
  しまう。いまは Ask 専用の指示を与える。フローは渡す(見えないものは説明できない)が、
  「このモードでは適用できないのでスキーマを出しても無駄である」と伝える。
- **ノードへのリンクはモードごとの機能ではない。** どちらのプロンプトも「エイリアスをバッククォートで囲む」ことを求め、サイドバーはすべてのアシスタント応答を同じように注釈する。だから応答中のノード名はリンクになり、クリックすればキャンバス上のそのノードが示される。指摘を役立つものにしているのは、ほぼこの一点である。
- **プロンプトに書くのはモデルが決めることだけである。** コードが自分で決めることは書かない。「差分であり、`delete` で削除」以上のマージの意味、レイアウト、コメントの積み方、つながれたノードがどの枠に入るか、空になった枠の扱い、`flow` のないノードがどのタブに入るか、などである。書けば毎回のトークンを消費し、コードが変わるたびにプロンプトが古くなる。理由はプロンプトではなくここに書く。
- **適用側はいまもモードで分岐しない。** 適用の中身を分岐させると片方だけ壊れるバグの
  温床になるため、適用処理はモードをほとんど見ない(部分スキーマのマージのために
  Agent かどうかを解釈側へ渡すだけ)。モードが決めるのは「どのプロンプトを送るか」で、
  それを決めるのはサーバ側である。モデルに何を伝えるかを握っているのはそちらだからである。

## 3. 適用の3段階（削除 → 追加/更新 → 接続）と、その順序の理由

再構築は必ず次の順で処理する。**順序そのものがルール**であり、1つのスキーマが自己矛盾していても
破綻しないための設計である。

### 第1段階: 削除
- 削除指示(エイリアスに空を指定したもの)で名指しされたノードを、スナップショットのフローから除く。
- 除いた ID を覚えておき、**第2段階が同じエイリアスを再び持ち込むのを禁じる**。
- **理由**: 「いったん消して作り直す」系の応答では、削除対象と同じ名前の新規ノードが同じスキーマに
  同居することがある。そのとき削除の意図を優先できる。

### 第2段階: 追加・更新
- 残ったフローをノード ID 引きにして、提案されたノードをマージする。
- **Config Node 保護**: 既存にない config ノードは追加しない(§5)。
- **ワイヤは足し算でマージする**: 既存ノードと一致した場合、既存の接続先と提案された接続先を
  出力ポート単位で足し合わせる。**接続を切るのは明示的な切断指示だけ**(§4)。
- **プロパティ保存**: LLM が触れていないキーは既存の値に戻す(§4)。

### 第3段階: 接続
- **1つに統合した索引**を作る(ここが肝心である):
  - 既存ノードの自動エイリアス、新規ノードが名乗るエイリアス、ノード名、ID を、すべて同じ索引から引く。
  - これがないと「既存の inject から新規の function へ」という接続で、送信元は解決できても送信先が
    解決できない。新規ノードは自動生成では単に種類名になり、LLM が付けた名前と一致しないためである。
- 存在しない ID 宛のワイヤを取り除き、切断指示を適用してから、スキーマの接続を張る。
- **なぜ接続を最後にするか**: 接続の両端は「削除も追加も済んだ最終的なノード集合」に対して解決しな
  ければならない。削除・追加より先に接続を確定すると、すでに消えたノードやまだ無いノードを指してしまう。

## 4. マージのルール（既存を壊さないための優先順位）

### 4.1 ワイヤ: 既定は「足す」、切るのは明示されたときだけ
- 既存の接続先と提案された接続先を、出力ポート単位で足し合わせ、重複は取り除く。
- 切断するのは、LLM が接続の削除を明示的に書いたときだけである。
- **理由**: LLM は編集対象ノードの接続を書き落としがちである。省略を「切断の意図」と解釈すると、
  無関係な既存接続まで勝手に消える。「接続が勝手に切られる」という不満を生まないための既定。

### 4.2 プロパティ: 「言及していないキーは既存のまま」
- LLM が明示的に設定したキーの集合をどう得るか:
  - Vibe Schema 経路では、変換の時点で「スキーマに実際に書かれていたキー」を記録しておく。
  - Node-RED JSON を直接受け取った経路では、値が入っているキーをそう見なす。
- それ以外のキーは、既存ノードの値に戻す。
- ただし同一性(ID・種類)、配置(所属タブ・座標)、接続、エディタの編集状態、および
  メタデータは引き継がない。これらは「プロパティ」ではなく、別のルールが決めるものだからである。
  所属グループ(`g`)だけは例外で、**引き継ぐ**。グループのパスが書き込むのはこの編集が
  枠に入れたノードだけ(§15)なので、それ以外のノードの所属はここで生き残らなければ
  ならないからである(§12「差分適用を見送る条件」を参照)。
- **理由**: 変換時に型ごとの既定値(たとえば debug ノードの出力対象の指定)が補われても、ユーザーが
  以前に設定した値を上書きしない。「触っていない設定は保持される」を保証するためである。
- **新しい**ノードは、応答が書かなかったプロパティに型の既定値を入れる(`applyTypeDefaults`)。パレットから置いたノードと同じ状態にするためで、これがないと値のない必須プロパティ(`property` のない `split` など)が検証に失敗し、ノードに警告マークが付く。既定値のない設定ノードへの参照には "" を入れる。編集ダイアログが「なし」のときに書く値で、未定義のままだとノードを開いて閉じるだけでフローが未デプロイ扱いになる(`http in` の `swaggerDoc`)。編集した既存ノードは書き込み後に検証し直す(`RED.editor.validateNode`)。エディタが検証するのはインポート時と編集ダイアログを閉じたときだけだからである。

### 4.3 ノードの照合: 完全一致のみ、あいまい一致は使わない
- 提案されたノードを既存ノードに割り当てるときは、**エイリアスの完全一致だけ**で判定する。
- **理由**: LLM にはプロンプトで既存エイリアスをすべて渡してある。一致しないエイリアスは「新規に
  作りたい」という意図だと解釈できる。ここであいまい一致を許すと、新しく作りたい `inject_py_1` が
  既存の `inject` に前方一致してしまい、無関係なノードを黙って上書きする。**「取り違えて上書き」
  より「新規として追加」の方が安全である。**

## 5. Config Node 保護

- LLM は config ノード(ブローカー設定や実行環境設定など)を **作成も削除もできない**。既存のものを
  エイリアスで参照するだけである。これはプロンプトと適用側の両方で強制している。
- 参照の解決順は「対象フロー自身のエイリアス表 → **コンテキスト全フロー**のエイリアス表 → 同種が1つだけなら再利用」。
  - 2段目があるのは、config ノードがフローに属さないからである。プロンプトはコンテキスト全フローを通してエイリアスを振るので、モデルは `ui_group_test_2` を文脈からそのまま読める。一方、対象フロー単体の表では同じノードが `ui_group_test` だったり、そもそも載っていなかったりする。プロンプトを組み立てたのと同じ `UI.getFlowsByIds` の出力から**モデルが見た表そのもの**を作り直すことで、渡した参照が渡したノードに解決される。ノードの**同一性**の判定は意図的に広げない。エイリアスはフローをまたぐと衝突し、書き込んでよいのは対象フローだけだからである(§6)。
  - 値が config ノードのエイリアスと完全一致するプロパティは、`toNodeRed` が知っているキー名(`broker`、`group` など)でなくても解決する。誰も知らない contrib ノードは config プロパティに好きな名前を付けるし、`toIntermediate` は行きの変換でそこにエイリアスを書いている。これはその往復の帰り側である。「参照元とは別の型であること」を条件にしてあり、`mqtt-broker` の `broker: "localhost"` をホスト名のまま通すのと同じ規則である。
- 同種の config ノードが1つしかない場合は、その既存のものを再利用する。同じ設定が二重にできるのを
  防ぐためである。
- どこにも解決しなかった参照は**空にしてチャット欄で知らせる**(`Config node(s) not found: …`)。自動生成した仮 ID を
  そのまま残すと、存在しないノードを指したままになる。「設定が必要なノード」ではなく「壊れたノード」として
  現れ、しかもどちらにせよ無言である。
- **理由**: config ノードは認証情報や接続先といった「壊れると影響範囲が広い」共有資源である。LLM が
  勝手に作ったり消したりして他のフローを巻き込む事故を防ぐ。config ノードはすべてコンテキストに
  含めたうえで、「参照は自由、生成と削除は不可」という非対称なルールにしている。

## 6. マルチフロー: 1つのエイリアスは1つのノード

- **モデルにはコンテキストの全フローを通した1つのエイリアス番号を見せている**ので、各エイリアスはちょうど1つのノードを指す。インポートは何よりも先に、返答をその同じ番号(`contextAliasTable`。`UI.getFlowsByIds` から作り直す)で読み、`planByWorkspace` がコンテキストフローごとのサブスキーマに分ける。各サブスキーマは、そのフロー単体のインポートが解決するエイリアスで書く。
- **既存ノードは実際にあるタブで編集する。** そのノードに付いた `flow` は無視し、タブ間の移動はしない。
- **新規ノード**は、`flow` がコンテキストフローを指していればそこへ、なければつながる先や見出しを付ける先のフローへ、それもなければ既定のフローへ置く。そのタブで同じエイリアスが別のノードに付いていれば名前を変える。
- 削除、`reposition`、接続の削除は、名指ししたノードのフローへ送る。エイリアスと完全には一致しない名前は各フローで探し、ちょうど1つのフローだけが持つときに限って適用する。
- タブ間のワイヤは作らない。コンテキスト内の2つのタブを link ノードでまたぐ接続の削除は `severAcrossFlows` が切る([vibe-schema.md](./vibe-schema.md))。
- **理由**: タブ単体で番号を振ると、2つのタブのどちらにも `debug` ができる。返答をタブごとに読んだり、そのエイリアスを最初に持っていたタブを推定したりしていたことが、編集が別のノードに着地する原因だった。モデルが見た番号にはその曖昧さがない。

### 走査範囲はコンテキストフローに限定する（必須）

推定も、タブ名の解決も、複数フローへの振り分けも、**LLM にコンテキストとして渡したフロー**の中だけを
走査する。全ワークスペースを走査してはならない。

- **理由**: 自動生成されるエイリアスが一意なのは**フローの中だけ**であり、タブをまたげば普通に衝突する。
  「エイリアスはどのタブのものか」の対応づけは先に見つかった方が勝つので、全部を走査すると
  「タブバーで手前にあるだけの無関係なフロー」が同名のエイリアスを先取りし、編集がまるごとそちらへ飛ぶ。
  しかも適用は、マージ後の最終状態に含まれないものを**削除する**（フォールバック時は対象キャンバスを
  消してから作り直す）ため、対象を取り違えた場合の影響は追加では済まず、破壊的になる。さらにチェックポイントは
  コンテキストフローの範囲しか保存していないので、Restore でも戻せない。
- 範囲を絞ることで「書き込む範囲 ⊆ スナップショットに入っている範囲」が常に成り立ち、Restore が
  いつでも有効になる。
- アクティブタブが範囲外のとき(送信後にユーザーがタブを切り替えた場合など)は、アクティブタブではなく
  コンテキストフローを対象にする。範囲指定がない(フローを1つも選んでいない)ときだけ、従来どおり
  アクティブタブを対象とする。
- 実際に適用する直前の最終確認で、対象が範囲外なら**中止**する。
- リグレッションテスト: `test/unit/cross_flow_isolation.test.js`(エイリアス衝突 / タブ切替 / 複数フローへの
  波及 / 範囲外のタブ指定 / 範囲指定なしのときの後方互換 / 1つのエイリアスは1つのノード /
  プロパティ中のノード ID / ランタイムとエディタの番号の一致)。

## 7. スナップショットの完全性と junction / group

### 前提（Node-RED エディタの内部構造）
- タブを指定してノードを取り出すエディタの標準 API は、**通常ノードしか返さない**。junction と group は
  それぞれ別のレジストリで管理されており、専用の取得 API を呼ばないと手に入らない
  (Node-RED 4.1.7 のエディタクライアントで確認)。
- 復元処理と、差分適用がフォールバックしたときの適用は、対象タブの junction と group を**全部
  消してから**フローを入れ直す。したがって、スナップショットに入っていない要素はそのまま消える。
  さらに接続の段階で「作り直したフローに存在しない ID 宛」のワイヤは取り除かれるため、junction が
  スナップショットから欠けると、そこへ向かうワイヤまで行き先なしとして切られる。

### 設計（必要な場所だけが取り込む）
- フローを取り出す関数に「junction と group も含める」オプションを設け、有効にしたときだけ
  スナップショットに含める。エディタ標準のエクスポートは、junction を接続情報つきで正しく
  書き出してくれる。
- 適用時の再構築の土台、チェックポイントの保存、LLM に渡すコンテキストがこのオプションを使う。
- **配線の中継はユーザーのもので、モデルには見せない。** junction と `link in` / `link out` ノード
  (`isRoutingNode`)には中間表現でエイリアスを付けず、それらを通るワイヤをその先への接続として
  読む。`A → junction → B` も `A → link out ⇢ link in → B` も `A → B` と見える。モデルはメッセージの
  行き先を理解でき、エイリアスの割り当ても中継の有無で変わらない。応答がその接続を書き直すと、
  中継の横に直接のワイヤが足され、同じメッセージが二重に届いてしまう。そこで、同じポートから
  中継経由ですでに届くノードへのワイヤを応答が足した場合は取り除く(`dropWiresBesideRouting`)。
  接続を削除する応答は中継の中で切断し(`severConnections`)、編集で役目を失った中継は片付ける
  (`removeIdleRouting`)。他の接続はすべて削除前と同じに読める。詳細は
  [vibe-schema.md](./vibe-schema.md) を参照。モデルが中継を追加したり配置したりすることはない
  (`link call` は戻ってくる処理の一段なので中継ではなく、通常のノードとして扱う)。

### レイアウトから group を外す理由
- junction は座標と接続を持つので、キャンバス上の実体として扱われる。実際に配線が通る点なので
  レイアウトの隣接関係に含め、鎖はそこを通して並べる。そのあと junction は元の位置に戻す。
  **レイアウトが junction を自分で置くことはない。** 動くのはつなぐ先と一緒のときだけである。
  枠の外の junction と link ノードは、その先のノード(`link out` なら送り込むノード)が動いた分
  だけ付いていくので、2つの枠の間の junction は、上にノードが加わって下の枠が押し下げられれば
  下の枠と一緒に動く([layout.md](./layout.md#junction-ノードはつなぐ先に付いていく))。大きさは実寸の 10×10 で測り、何かが junction に重なればそちらを
  どける(枠の縁にある junction は普通の配線経路なので、そのままにする)。
- group も座標を持つため同じくキャンバス上の実体として扱われるが、**group の外形は自分のメンバーを
  囲むように決まる**。これを重なり解消の処理に渡すと「自分の中身と重なっている」と判定され、破綻する。
- そこで「キャンバス上の実体であり、かつ group ではないもの」という判定を別に設け、レイアウトの
  呼び出しにはこちらを使う。**group はレイアウトの対象から外し、位置は元のまま保つ。**
- 回帰テスト: `test/unit/junction_preserve.test.js`(`npm test` に登録)。junction を挟んだ流れを編集し、
  junction 自体と前後両方向のワイヤが残ること、つなぐ先が動かない編集では junction が動かず、配線が変わらず、
  何も上に載らないこと、2つの枠の間の中継が押し下げられた枠に付いていくこと、コンテキストが junction の先を読み、接続を書き直してもワイヤが増えない
  こと、接続の削除が junction / link ノードの中で切断され、他の接続が保たれ、役目を失った中継が消えること、link ノードのホバー時だけ見える仮想リンクで2本のシーケンスが1本にならないことを検証する。

### 巻き戻し用のバックアップにも同じ規則が効く
- どちらの適用方式も、ワークスペースに手を入れる前に自前のバックアップを取っておき、取り込みが
  失敗したときにフローを元へ戻す。このバックアップには**通常ノードしか入っていなかった**ため、
  「何も変えないはずの失敗経路」で junction と group だけが消えて戻らない、という状態に
  なっていた。
- バックアップに junction と group も含めるようにし、単純な JSON コピーではなくエディタ標準の
  エクスポートで作るようにした。エディタ上の group は、メンバーを**ノードの実体そのもの**として
  保持しているため、そのままコピーすると、取り込み側が ID の並びを期待している場所にノード全体が書き込まれてしまう。
- 回帰テスト: `test/unit/import_safety.test.js` のシナリオ B。

## 8. レイアウトの優先順位（詳細は layout.md）

- **既存フローがある場合は差分配置**: 既存ノードの座標は編集前の位置に戻し、新規ノードだけを
  隣接ノードの右または左に置く。既存の形はそのまま保つ。
- **完全な新規のときだけ全体再配置**。長い鎖は**折り返さない**。枠がシーケンスを読みやすくしているうえ、
  1つ2つのノードだけが別の行に回る折り返しは、長い1行より読みにくかったためである。
- **間隔は「ノードの縁と縁のあいだの余白」**であり、中心間の距離ではない。ノード幅は、可能なら
  エディタが実測した値を使い、名前が変わって実測値が当てにならないときは推定値に切り替える。
- 再配置指示は名指しされた一群だけを並べ直し、元の左上位置に戻すので他は動かない。削除して作り直すと
  ID が変わってしまうため、ID を保ったまま整列し直せることに意味がある。

## 9. チェックポイント(巻き戻し)の考え方

- 適用の**直前**に対象フローをスナップショットに保存し、それを該当メッセージに紐付ける。
  メッセージ横の Restore ボタンがそこまで巻き戻す。
- チェックポイントは `MAX_CHECKPOINT_FILES` を超えたら古いものから削除する。
- 整理は書き込みの**後**に行う。先に整理すると、新しいレコードが載った時点で上限＋1件に
  なってしまい、上限が言葉どおりの意味を持たなかった。メモリのみの経路(先に入れてから
  詰める)とも、同じ定数について食い違っていた。
- 復元は、対象タブのタブ以外の要素(通常ノード・サブフローの実体・junction・group)を、それぞれの
  種類に応じた API で全部消してから、スナップショットを入れ直す。
- スナップショットに junction と group が含まれていること(§7)が、復元で消えないための前提である。
- Restore 後はワークスペースを未保存状態にし、ユーザーがデプロイして確定できるようにする。

## 10. セキュリティ/境界の既定（前提）

- 全 HTTP エンドポイントは Node-RED の管理用ルート上にあり、データを扱うルートには
  `RED.auth.needsPermission` を明示的に付けている。Node-RED は自前で `adminAuth` を
  プラグイン登録ルートへ広げてはくれないためである。クライアントは `Common.apiFetch` 経由で
  エディタのベアラートークンを送る。静的アセットのルートは意図的に未認証のまま残している
  (タグ読み込みでヘッダを送れず、配るのはプラグイン自身の公開済みコードのみ)。
- API キーはプラグインの他の状態と同じ `<userDir>/llm-plugin` に暗号化して保存する(AES-256-GCM。旧 CTR 形式も読める)。ログ・エラー・
  クライアントログは出力前に秘匿情報を除去する。LLM へ送るフローコンテキストからも
  認証情報を取り除く。
- **Agent モードは受け入れたリスクの境界**: モデルの出力を確認なしで適用し、その中には
  `function` / `exec` ノードが含まれうる。すなわち設計上、任意コード実行である。
  ノード種別の許可リストは設けない(設けるとこのモードの意義が失われる)。詳細は
  architecture.md を参照。

## 11. 議論したい論点 / 既知のトレードオフ

このドキュメントを土台に議論したい主なポイント:

1. **group をどの型に分類するか**: 型判定は構造から推測する仕組みになっているため、group はエクスポート
   前は config ノード扱い、エクスポート後(座標が付いた状態)ではキャンバス要素扱いになる。現状は
   「レイアウトからだけ外す」ことで辻褄を合わせているが、group と junction を型判定そのものに明示的に
   書くべきかどうか。
2. **あいまい一致をどこまで許すか**: ノードの照合は完全一致のみだが、地の文のノード名注釈やヒントの
   事前解決ではあいまい一致を使っている(一定の長さ以上かつ候補が1つに絞れるときだけ)。この線引きが
   妥当かどうか。
3. **エディタ認証への対応**: 認証を有効にした環境をサポート範囲に入れるかどうか。

### 参考: エイリアス解決の優先順位
上から順に試し、最初に当たったものを採用する:

1. ID の完全一致
2. エイリアスの完全一致
3. 記号や大文字小文字のゆれを吸収した正規化後の一致
4. ノード名の一致
5. **完全一致のみを要求する呼び出しは、ここで打ち切る**
6. より緩い形でのエイリアス一致
7. 近似一致(一定の長さ以上あり、かつ候補が1つに絞れるときだけ)

「完全一致のみ」の指定は、ノードの照合(§4.3)や、ヒント・指示の事前解決で使う。弱い一致が
別のノードの ID を奪ってしまうのを防ぐためである。

## 12. 「作り直し」ではなく「差分適用」

### 作り直し方式の何が問題だったか
組み立て処理は、対象タブの**あるべき最終状態を丸ごと**作る。以前の適用はそれを最も単純な方法で
実現していた。タブの中のノード・junction・group を全部消してから、組み上がった一式を同じ ID のまま
入れ直す。結果は正しいが、そこに至る過程で**編集に無関係なノードまで一度破棄して作り直していた**。
エディタ自身の undo は筋が通らなくなり、スナップショットに漏れがあれば、それはそのまま削除に
なった（junction と group が消えていたのはこれである。§7）。

（なお、キャンバスの選択状態はどちらの方式でも解除される。再描画の共通処理が、描き直す前に
「選択をすべて解除」を実行するためである（消えたノードが選択に残ってはいけない）。差分適用が
狭めるのは「破棄される範囲」であって、「選択が解除される範囲」ではない。）

### 誤解しやすい点：デプロイでの再起動は起きていなかった
この方式でも、デプロイ済みのランタイムでノードが再起動されることはなかった。何を止めて何を
起動し直すかは Node-RED ランタイムの差分判定が決めており、その判定はノードを ID で突き合わせた
うえで **`x` / `y` / `wires` を意図的に無視する**（group ではさらに `nodes` / `style` / `w` / `h`）。
作り直しは ID を保持し、触っていないノードはスナップショットからそのまま持ち越すので、それらが
「変更あり」に分類されることはない。この性質は `test/unit/deploy_churn.test.js` が同じ判定基準を実装して固定している。

（**Full deploy** は無条件に全再起動する。**Modified Flows** は配線が変わったノードや link で
つながったノードも止める。どちらもデプロイの種類の選択によるもので、適用方式の問題ではない。）

### 差分適用の分類
最終状態は同じまま、現在のキャンバスとの差分として当てる。

| 分類 | 処理 |
| --- | --- |
| 今あるが、もう不要 | 種類ごとの削除 API で消す |
| 必要だが、まだ無い | まとめて1回の import に渡す |
| 両方にあり、プロパティが違う | エディタ上のノードに直接書き込む |
| 両方にあり、座標だけ違う | 位置を代入して移動扱いにする |
| 両方にあり、配線が違う | リンク操作（下記） |
| 両方にあり、同一 | **一切触らない** |

### ワイヤは配列ではなくリンクである
エディタにおいて `node.wires` は正本ではない。接続は `{ source, sourcePort, target }` という独立した
オブジェクトとして別のレジストリに保持されており、エクスポート時にそこから `wires` が**導出**される。
つまり `node.wires` に代入しても何も変わらない。したがって配線の変更は、エディタ上のノードオブジェクトに
対してリンクの追加・削除 API を呼んで行う。削除 API は**オブジェクトの同一性**で照合するため、消す
リンクはエディタから取得したものでなければならない。組み立て直したリンクオブジェクトは何にも一致せず、
黙って無視される。追加ノードの import は配線処理より**前**に行う。新しいリンクは両端が存在しないと
張れないからである。

ここから2つの順序上の注意が出てくる。
- import がリンクにするのは、**同じ import に含まれるノード**へのワイヤだけである(red.js の
  `importNodes` は自分の `node_map` を通してリンクを作る)。したがって、再 import されなかったノード
  から追加ノードへ**向かう**ワイヤも、追加ノードから既存のノードへ**出る**ワイヤも、import では
  できない。どちらも配線処理が作る。後者はテスト用のモックが任意の既存ノードにリンクしていたために
  長く見逃され、既存の `ui-text` の手前にノードを挿入する編集で、エディタではそのワイヤが消えていた。
  モックは今、エディタと同じく1回の import の中だけでリンクする。
- config ノードへの参照を張り替えるプロパティ更新では、書き込む**前に古い値に対して参照解除**を行い、
  書き込んだ後に登録し直す。そうしないと config ノード側の利用者リストに、もう使っていないノードが
  残り続ける。

### 差分適用を見送る条件
安全に表現できない変更に出会ったとき、差分適用は自分では処理せず、呼び出し側が従来の作り直し方式へ
フォールバックする。

- 既存の ID の type が変わった
- エクスポートを往復できないキャンバス要素がタブに存在する
- どちらかの側に group があり、かつ **group 用の API が使えない**（後述）

**この判定が意味を持つには、マージで `g` が生き残っている必要がある。** `g` は
`MERGE_SKIP_KEYS` に入れてはいけない。他のどこでも埋め直されないため、入れると編集した
ノードが必ずグループ所属を失って返ってくるからである。それ自体が静かなデータ損失であり
（ノードはグループを抜けるのに、グループ側はそのノードを挙げ続ける）、同時に「group 所属が
変わった」判定が**通常のプロパティ編集のたびに**成立してしまう。つまりグループを使っている
フローでは差分適用が毎回見送られ、作り直しが走っていた。`g` を無条件に引き継いで安全なのは、
`g` が変換側の `META_KEY` だからである。スキーマからは読むことも書くこともできないので、
既存の値以外にありえない。

ノードが属せる枠はただ1つである。したがってスキーマがメンバーを移したら、元の枠の一覧からは
外れなければならない。両方の一覧が同じノードを挙げている間は、古い枠が「もう持っていない
ノード」に届くようキャンバスを横切って伸びたままになり、どちらの所属が勝つかはグループが
書かれた順序次第になっていた。また「このノードをあの枠に入れて」は所属を動かすのであって
ノードを動かすのではない。枠が持つのは1本のシーケンスだけなので(§15)、枠に加わるノードは
必ずその中のシーケンスの一部であり、通常の配置処理がすでに隣へ置いている。

この関係のもう半分が group 自身の `nodes` 一覧で、こちらは Node-RED が自動では整合させない。
`RED.nodes.remove` にはグループの後始末が一切ない（エディタ標準の削除操作は先に
`RED.group.removeFromGroup` を呼んでいる）。両者を揃える処理が2箇所に要る。

- **マージ後の最終状態の側**: 削除の段階で、ワイヤを取り除くのと同じ要領で各 group の
  `nodes` からも削除済みの ID を落とす。適用処理に渡る時点で整合が取れている。
- **エディタのキャンバスの側**: ノードを削除する前に `RED.group.removeFromGroup` を呼ぶ。
  group はメンバーを**ノードの実体そのもの**として保持しているため、エクスポート形式の ID の
  配列を書き換えても反映されない。これが唯一の正しい手順である。先にノードを削除すると、
  group が存在しないノードを指し続けることになる。

group の `nodes` をプロパティ比較の対象から外している（`w` / `h` と同じ扱い）のはこのためである。
3つともメンバーから導かれる情報であり、所属の正本はノード側の `g` で、そちらは比較している。
一覧まで比較すると、所属の変更が2重に報告される。

**もう半分を書くのが `applyGroupMembership` である。** スキーマは今やモデルに箱を要求する
（§15）ので、所属が変わる編集は例外ではなく通常のケースになった。見送っていると、ほとんどの
応答で作り直しが走り、デプロイ時のノード再起動とあのログ行が毎回ついてくる。そこで差分適用が
自分で所属を書く。import の**後**に置くのは、この編集で追加されたメンバーは、箱に入れる前に
存在していなければならないからである。

- **まず出す側**: 箱から外れたノードと、箱そのものが削除されたノードを
  `RED.group.removeFromGroup` で切り離す。`RED.nodes.removeGroup` はメンバーの `g` を
  消してくれないし、`g` こそエディタが描画に使う半分である。
- **次に一覧を「代入」する**: 部分的に差し込むのではなく、望む状態のメンバーを実体に解決して
  そのまま入れ替える。エディタが実体ではなく ID のまま残した要素は、まさに「空の箱」が
  描かれる形である。
- **枠も一緒に書く**: Node-RED が group の外形を計算し直すのは、ユーザーがメンバーを
  ドラッグしたときだけである。したがってレイアウトが合わせた枠が、そのままユーザーの見る枠に
  なる。`RED.group.addToGroup` を使わないのもこれが理由で、あちらは `n.w` / `n.h` から枠を
  計算し直すが、まだ描画されていないノードはその値を持たない。
- **どちらかの側に箱があれば必ず走る**: 枠とメンバー一覧は導かれる情報なので比較しておらず、
  「何も変わっていない」を差分から読み取ることができない。この処理は冪等で、変更のない group に
  対しては元と同じ内容を書き戻すだけである。

`removeFromGroup` はワークスペースがロックされていると何もせずに戻る。ここではその「黙って
何もしない」が最悪の結果になる。ノードだけが消え、group はそれを指したまま残るからである。
そこで差分適用は group 用の API が使える状態かを先に確認し、使えなければ見送る。作り直し方式は
この API を必要としない（group ごと入れ直すため）ので、同じ整合の取れた最終状態に、
より広い経路で到達する。

**正しさが「差分適用が全ケースを網羅していること」に依存しない**という点は変わらない。
作り直し方式はより広い経路で同じ最終状態に到達するので、group まわりのどのケースも、
最後はそこへ落とせる。

### 失敗したときの戻し方
差分の途中で例外が出ると、キャンバスは中途半端に適用された状態になる。これは入れ直すだけでは
戻せない（追加された分が消えない）。そのためエラー経路では、タブを消してから「適用前」の
エクスポートを入れ直す。これは比較の土台に使ったものと同一のエクスポートなので、「適用前とは
何だったか」で両者が食い違うことはない。

**config ノードには専用の巻き戻しが要る。** config ノードは `z` を持たないためワークスペースの
エクスポートに最初から入っておらず、キャンバスを戻しても手が届かない。そのため以前は、失敗した
適用が「フローは無傷に見えるのに、接続先のブローカーだけ書き換わったまま」という状態を残していた。
そこで config ノードに触るときに、「これは元々存在しなかったので消し直す」か「上書きするキーの
元の値」かを記録しておく。値の記録は `hasOwnProperty` で判定するので、元々無かったキーは
`undefined` を書き戻すのではなく削除される。巻き戻しは新しいものから順に、かつキャンバスの復元の
**後**に行う。ワークスペースのノードを消すと、それらが config ノードの利用者リストから先に外れる
ためである。値と一緒に `changed` も戻す。このフラグはデプロイが読む対象なので、立てたままにすると
「当たらなかった編集」のために config ノードが再起動されてしまう。

- 回帰テスト: `test/unit/incremental_apply.test.js`（何が触られたか）、
  `test/unit/deploy_churn.test.js`（何が再起動されるか）、
  `test/unit/import_safety.test.js` シナリオ B（キャンバスの巻き戻し）と
  シナリオ D（config ノードの巻き戻し）

## 13. 適用は順序づけない

別々のチャットの応答や、古い応答に対する Apply Again は、どんな順序でもキャンバスに
届きうる。**キューには入れない。** 各適用は行われたときに、その時点のキャンバスへ
マージされる。

- 各適用は実行の直前に自分のチェックポイントを保存する。それを復元すると対象フローは
  その時点の状態に戻り、それより後に適用されたものも取り除かれる。
- 書き込みそのものは引き続き Node-RED が守る。古いリビジョンに対するデプロイは `409` で
  返り、エディタ標準のマージ競合ダイアログが開く。
- **キューを置かない理由。** 以前は適用済みかつ未デプロイのフローをデプロイまで保留し、
  そのフローへの他の編集を待たせていた。レビューの時間は守れたが、同じチャットで続けて
  出した指示が、まだ誰もするつもりのないデプロイを待つことになり、そこから抜けるだけの
  ためにパネル、Release ボタン、タイムアウトが必要だった。いまレビューを支えるのは
  チェックポイントと、デプロイが利用者の判断であることである。

## 14. 壊れた値の2通りの読み方

応答の JSON は、途中で切れているよりも「クォートが1つ足りない・1つ多い」形で届く方が
はるかに多い。だから `llm_json_parser` は応答全体を捨てるのではなく修復する。クォートの
修復は、人が読むときと同じ読み方をする。開きクォートから、`,` や `}` や `]` が続く
クォートまでが値であり、その間にあるクォートはエスケープする、という読み方である。

この読み方は文字列に対しては正しい。式に対しては誤りである。

```
"to": "WARN " & payload.line & "C",
```

モデルが書きたかったのは JSONata の式 `"WARN " & payload.line & "C"` であり、その先頭と
末尾の文字はこの式自身のクォートである。ところが修復はその2つを値の区切りと読み、中央の
2つをエスケープする。結果として「妥当な JSON・妥当な Vibe Schema・Node-RED が受け付けない
式」ができあがる。ノードはインポートされ、そのうえで JSONata のエラーを表示する。この
時点で式は「たまたま構文が通らない文字列」でしかないので、後続の処理では気づけない。

どちらの読み方も現実にありうるので、パーサは原則としてどちらかを優先しない。「そもそも
どちらが式なのか」を問う。JSONata では文字列リテラルは必ず演算子で前後とつながるので、
2つのリテラルに挟まれたコードは、先頭と末尾の両方が演算子になる。修復がエスケープした
クォートで値を分割すると、この検査を通るのは片方だけである。

| 修復が作った値 | そのまま読む | 式として読む |
|---|---|---|
| `WARN " & payload.line & "C` | `WARN ` はコードでない ✗ | `" & payload.line & "` — 両端が演算子 ✓ |
| `payload.a & "x" & payload.b` | `payload.a & ` … ` & payload.b` ✓ | `x` はコードでない ✗ |

通るのがちょうど1通りのときだけ、パーサはその読み方を採用し、その読み方が「式自身の
ものだ」と言うクォート(先頭・末尾・その両方)を戻す。どちらも通らないとき — function の
本体にある `f"text {var}"`、語句を引用した文章など — は、修復が作った値をそのまま残す。
どちらにも転びうる推測はしない。

システムプロンプトは、そもそも JSONata を避けさせる。値は素の型で書き、文字列は template
(mustache 記法の `{{payload}}`)で組み立て、計算は function で行う。実測のシナリオで小さな
モデルが最も多く間違えたのが JSONata であり、ユーザーがやり取りの中で見た傾向も同じだった。
ユーザーが JSONata を求めたときは、同じ理由で式の中の文字列リテラルに単一引用符を求める。
`'C'` と書けば JSON 側のエスケープが要らなくなり、そもそもこの経路に入らずに済む。

修復がもう1つ知っていなければならないことがある。値が1つ壊れているだけで**ブロック全体**が
この修復を通るからである。すなわち、**配列**の中の文字列は鍵ではなく値である。修復はこれを
「手前に `:` があるか」で判定していたが、`["a", "b"]` の中にはそれがない。結果として各要素が
鍵として読まれ、鍵の終わりは `,` ではなく `:` なので、カンマが文字列に飲み込まれていた。
式が1つ壊れただけで、同じ応答の `reposition` やグループのメンバー一覧がまるごと壊れうる。
現在はカーソルがどの容器の中にいるかを追い、配列の中の文字列は常に値として扱う。

- リグレッションテスト: `test/unit/json_repair.test.js` — 式が自身のリテラルのクォートを保つこと
  (2つ失う場合と、末尾の1つだけ失う場合の両方)、すでに正しく読める連結や三項演算子を
  囲み直さないこと、function 本体の f 文字列を相変わらず放っておくこと。

## 15. フロー・タブ・グループ

Node-RED は2つの別物をどちらもフローと呼ぶ。**タブ**と、**一連のつながったノード**である。
ユーザーはその両方の意味で使い、しかも同じ一文の中で混ぜる。そしてこの曖昧さは、いちばん
損をする場所に着地する。「ここにフローを3つ作って」が、タブ3枚と読まれたり、1本の鎖に
分岐を3つ付けたものと読まれたりする。求められていたのは、横に並んだ3本の独立した並びである。

そこでスキーマ側で決めてしまう。ノードの `flow` は**常にタブのラベル**である。1つのタブは
つながっていない並びを何本でも持てるし、レイアウトはすでにそれぞれを自分のバンドに置いている。
つまりキャンバス側は変える必要がなかった。足りなかったのは「一緒に頼まれたからといって別々の
並びを1本に繋いではいけない」という指示である。**プロンプト**にこの区別を明記し、フロー /
並び / パイプラインを複数求められたら、それぞれ自分のトリガと終端を持つ独立した並びをその数
だけ作るよう指示した。これがないとモデルは自分がいちばん慣れた形、つまり1つのトリガから
伸びる1本の鎖に寄る。

### グループの枠はユーザーのもの

グループ、すなわちエディタがノードの集まりに描く枠は、**スキーマに含めない**。以前の版では
モデルが枠を宣言し、広げ、入れ子にし、削除できた(`groups: { alias: { name, nodes } }`)。
これは取りやめた。枠はユーザーが描いたものであり、応答がそれを描き直せると、応答が触れて
いないものは残すという規則(§0)が崩れる。現在は次のとおりである。

- コンテキストには枠を1つも載せない。`toIntermediate` はグループを落とすので、枠があっても
  なくてもノードのエイリアスは同一になり、インポート側が再現しなければならない連番(§6)は
  動かない。
- 応答の `groups` キーは無視し、`groups` だけの応答はスキーマとみなさない(`isVibeSchema`)。
  枠を作ることも、編集することも、削除することもない。
- プロンプトは枠について何も書かない。枠がどうなるかはコードが決めることである(§2)。

コンテキストの書き出しには今もグループが含まれる(`includeCanvasExtras`)。junction を
含めるためであり、枠は変換器が落とす。

### 1つの枠に1本のシーケンス

枠は**つながった1本のシーケンス**、つまりワイヤのグラフの連結成分1つだけを持つものとみなす。
junction を通るワイヤはつながりに数える。link ノードの仮想リンク(エディタがホバー時だけ
描くもの)は、コンテキストでは接続として見えていても数えない。見出しのコメントと入れ子の枠は
シーケンスに数えない。編集は枠をこの状態に保つ(`keepBoxesAroundTheirSequences`)。

- **枠で囲まれたシーケンスにワイヤでつながれた新しいノードは、その枠に入る。** ただし隣接
  ノードの枠がすべて同じ1つである場合に限る。枠の外に残すと、属しているはずの枠から
  揃え処理によって引き離されていた。
- **見出しのコメントは、見出している枠に入れる。** パディングはちょうど1行分なので、先頭の
  メンバーに貼り付けたコメントは枠の上辺にぴったり載り、見出しではなく迷子のラベルに見える。
  **コメントをどこに置くかはモデルが決める。** コンテキストには各コメントの現在の `above` を
  載せ、応答が `above` を指定したコメント(新規でも既存でも)は、そのノードの直上に置いて
  ノードに従わせる。ノードの枠があればそこへ入り、なければ元の枠から出る。応答が触れない
  コメントは枠をそのまま保つ。
- **2つの枠をワイヤでつなぐ**のはワイヤだけの変更である。どちらの枠も、持っていたメンバーと
  ともにその場に残る。シーケンスは2つの枠にまたがることになり、各枠はその一部を1つずつ持つ。
- **枠が暗黙に消えることはない。** メンバーがすべて削除されても、ユーザーが空の枠を描いて
  いても、枠は残る。エディタも同じである。削除したメンバーはグループの `nodes` から外す。
  `RED.nodes.remove` はグループの帳尻を合わせないからである(§12)。

メンバーシップはエディタ側でも両面である。メンバーの `g` と、グループの `nodes` に並ぶ ID。
`g` を書き込むのは、この編集が枠に入れたノードだけにしている。既存グループ自身の帳尻は
無関係な編集が触る話ではないし、「直す」と変更として検出され、適用全体が作り直しの経路へ落ちる。

### 枠はこちらで計算する

Node-RED はグループに `x`/`y`/`w`/`h` を保存し、ユーザーがメンバーをドラッグしたときにしか
再計算しない。だからレイアウトがメンバーを動かしても、枠は元の場所に残ってしまう。
`CanvasLayout.fitGroups` がレイアウトのあとに、エディタ自身と同じ 25px のパディングで
すべての枠を合わせる([layout.md](./layout.md#グループの枠))。ユーザーが大きくした枠も含め、
すべての枠を中身にぴったり合わせる。中身より大きい枠は、中身を基準に揃えたり離したり
できないからである。

- リグレッションテスト: `test/unit/group_schema.test.js` — 応答は枠を作れず、編集も削除もできない
  こと。コンテキストに枠が現れず、ノードのエイリアスも動かないこと。枠にノードを足すと次の
  並びが丸ごと下へ押されること。枠の中の並びを並べ直すと枠が合わせ直され、見出しのコメントが
  そのノードに付いていくこと。メンバーがすべて削除された枠も、空の枠も残ること。2つの枠を
  ワイヤでつないでもどちらも動かないこと。枠で囲まれたシーケンスにつながれた新しいノードが
  その枠に入ること。枠内に追加した分岐が他と重ならずポート順に並ぶこと。応答が指定した
  ノードへコメントが移り、その枠に入ること。枠の中のノードの上に置いた新しいコメントが枠の
  内側に描かれること。junction と link ノードの側は `test/unit/junction_preserve.test.js` が扱う。
