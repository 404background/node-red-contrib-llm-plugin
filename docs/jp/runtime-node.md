# LLM Plugin — ワークフローノード

サイドバーと並んで登録されるランタイムノード(パレットカテゴリ **llm-plugin**)。フローから
LLM を呼び出せる。プロバイダ・モデル・対象フローはノードに設定し、API キーと URL は
**LLM Plugin サイドバー**(Settings)から継承する。

## `LLM` ノード(`llm-request`)

| フィールド | 説明 |
|-------|-------|
| Mode | **Ask** — `msg.payload` に応答。**Agent** — 同じことをした上で、開いているエディタに変更をライブ適用する。 |
| Provider | Ollama / OpenAI / Custom。キー & URL はサイドバー由来。 |
| Model | フリーテキスト(例: `llama3.1`, `gpt-4o-mini`)。**必須**。`msg.model` でメッセージ単位に上書き。 |
| Flows | 複数選択(なし / 1つ / 複数)。**両モード**で LLM にコンテキストとして送られる。ノードを開くたびにリストが更新される。 |
| API URL | フローコンテキストを読むための Admin API ベース — 通常はエディタが配信される URL(スタンドアロン `http://localhost:1880`。埋め込み: `httpAdminRoot` ベース、例 `http://localhost:8000/red`)。文字列または **flow/global** コンテキスト変数を受け取る。空欄 = 自動検出(推奨。非 1880 ポートに埋め込まれても動く)。`msg.editorUrl` で上書き。設定した URL が失敗した場合、ノードは警告付きで自動検出にフォールバックする。 |
| Timeout | 秒。デフォルト **3600**(1時間 — ローカル LLM は遅いことがある)。`0` = 無制限。`msg.timeout` でメッセージ単位に上書き。 |
| Auto deploy | **Agent 専用、開発者向け機能。** チェックすると、変更を適用した直後にエディタがデプロイする。実行するのはエディタ自身の Deploy 操作で、確認ダイアログを出さない形で呼ぶ。無人のループが確認待ちで止まらず、未保存状態も正しく解消されるためである。デプロイは非同期で進み、結果はエディタ自身のデプロイ通知が報告する。レビューの機会はない。エディタは1つだけ開くこと。デプロイ種別は Modified Nodes / Modified Flows を推奨。使い捨ての開発インスタンスでのみ使うこと。 |

**入力:** `payload`(プロンプト。文字列は改行を正規化、オブジェクトは JSON 文字列化)。
**出力:** `payload`(テキスト応答 — `JSON.parse` しないこと)、`llm`
(mode/provider/model/elapsed)、Agent モードでは `flow`
(`{ targetFlows, dispatchedToEditor }`)。

**ステータス:** リクエスト中は青ドット(経過秒を刻む)、成功時は緑 `done (…)` / `sent to editor`、
失敗時は赤 `error` / `timeout`。

## Agent モードが変更を適用する仕組み

ランタイムノードはブラウザのキャンバスを直接編集できない。そこで応答を Node-RED の通信チャネルへ
流し、エディタ側で動いているノードの UI 部分がそれを受け取って、プラグインのインポート処理に
渡す。サイドバーとまったく同じ経路である。

- プラグインが読み込まれた**エディタが開いている必要がある**。ヘッドレス実行にはキャンバスがない。
- このノード経由の操作には**チャット履歴も Restore Checkpoint もない**(サイドバーとの違い)。
  デプロイ前にキャンバス上でレビューすること。必要ならエディタの取り消し操作を使う。
- 意図的に**「deploy」ノードは用意していない。** サーバ側のノードからエディタの Deploy ボタンは
  再現できない。デプロイの対象はブラウザ側が持っているエディタの状態であり、これは純粋に
  クライアント側のものだからである。Agent モードは編集をその場で反映するので、ユーザーが自分で
  デプロイする。あるいは **Auto deploy** をチェックすれば、エディタ側が反映直後にエディタ自身の
  デプロイ操作を呼ぶ。サーバ側の deploy ノードでは無理だったことがこれで成立するのは、
  ブラウザ自身がデプロイしているからである。

## ファイル

```
node/
  lib/admin_api.js              フローを読み出す管理 API クライアント(接続先を自動検出)
  llm-request/llm-request.js    ランタイム: プロンプト構築 + プロバイダ呼び出し + エディタへの送信
  llm-request/llm-request.html  エディタ: 設定 UI + 受け取った応答をフローへ反映する処理
```

設定・認証情報・プロバイダごとの呼び分け・プロンプト構築を担う共有 LLM エンジンは
[`../../src/llm_core.js`](../../src/llm_core.js) にあり、サイドバーと共用している。

## 例

**Menu → Import → Examples**(または `examples/` の JSON ファイル)からインポート:

- `llm-nodes` — Ask と Agent を並べたもの(コアノードのみ)。Agent 行の編集は開いているエディタに
  ライブ適用される。レビューして手動で Deploy する — 自動デプロイは一切なし。
- `llm-self-feedback` — **開発者向けサンプル**: HTTP in/request ノード上の Agent + Auto deploy
  自己フィードバックループ。5イテレーションでハードキャップ(各ループは LLM リクエスト1回と
  デプロイ1回を要する — キャップは絶対に外さない)。イテレーション1が別の対象タブに小さな
  デモフローを作り、以降のイテレーションがそれぞれ改善する。LLM が完成と判断して `END` と応答する
  (ループの `next loop URL` 関数がチェック)か、キャップに達するまで続く。実行前に **Modified Flows**
  デプロイタイプを選び、ループフロー自体がイテレーション途中で再起動されないようにする。インスタンスの
  HTTP API エンドポイントベースは change ノードで1回設定する(フロー変数 `apiBase`、デフォルト
  `http://127.0.0.1:1880`)— 埋め込みインスタンスではそこで編集する(例 `http://127.0.0.1:8000/api`)。
